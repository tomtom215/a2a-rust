# Adversarial probe

Black-box, over-the-wire adversarial harnesses for a **running** A2A server —
one per request binding:

| Probe | Binding | Deps |
|---|---|---|
| `probe.py` | JSON-RPC (spec §9) | stdlib only |
| `probe_ws.py` | WebSocket (spec §12) | stdlib only (RFC 6455 client built in) |
| `probe_grpc.py` | gRPC (spec §10) | `pip install grpcio grpcio-tools` (compiles the proto at startup) |

They are the third leg of this project's negative-input testing, distinct from
the other two:

| Layer | Where | What it proves |
|---|---|---|
| Unit / property tests | `crates/**/src/**` | a function rejects bad input in isolation |
| In-process fuzzing | `fuzz/` | the parsers survive libFuzzer-generated bytes |
| **Adversarial probe** | **`scripts/adversarial/`** | a **live** server, backed by a real model, stays up and answers safely under attack |

The probe sends malformed, hostile, and edge-case requests to a real server and,
after **every** request, re-probes `GET /.well-known/agent-card.json` to confirm
the server is still alive. A production A2A server must answer every case with a
structured JSON-RPC error (or a clean HTTP 4xx) and keep serving — never crash,
hang the whole process, reset the connection, return a 5xx, leak an internal
path or panic message, or silently accept what it was built to reject.

The guiding rule is the project's own: **test and verify, never assume.** The
harness reports only what it observed on the wire.

## Running it

Start a model and an agent, then point the probe at the agent:

```bash
# 1. a real model on the OpenAI-compatible port (llama.cpp / vLLM / Ollama)
llama-server -m qwen3.5-0.8b.gguf --host 127.0.0.1 --port 11434 &

# 2. the genai example in server mode (SSRF guard ON by default)
GENAI_MODEL='qwen3.5:0.8b' A2A_BIND_ADDR=127.0.0.1:8080 \
    cargo run -p genai-a2a-agent &

# 3. the probe
python3 scripts/adversarial/probe.py --port 8080
```

No third-party Python packages are needed (standard library only).

### The WebSocket and gRPC bindings

`genai-agent` server mode serves JSON-RPC only by default, but it will also
bind gRPC and WebSocket on request — the three then share one process, so the
companion probes use the JSON-RPC port for process liveness:

```bash
GENAI_MODEL='qwen3.5:0.8b' \
  A2A_BIND_ADDR=127.0.0.1:8080 \
  A2A_GRPC_ADDR=127.0.0.1:8081 \
  A2A_WS_ADDR=127.0.0.1:8082 \
  cargo run -p genai-a2a-agent &

python3 scripts/adversarial/probe_ws.py   --ws-port 8082   --http-port 8080
pip install grpcio grpcio-tools   # gRPC probe only
python3 scripts/adversarial/probe_grpc.py --grpc-port 8081 --http-port 8080
```

`probe_grpc.py` compiles the repo proto to stubs at startup (stripping the
google.api gateway options, which does not change any wire format), so it needs
`grpcio`/`grpcio-tools`; the other two are stdlib-only.

### Options

```
--host HOST              default 127.0.0.1
--port PORT              default 8080
--categories ABCDEF      run a subset (default: all)
--expect-ssrf-guard      treat an accepted private/loopback webhook as a DANGER;
                         use against a server WITHOUT allow_private_urls()
--json PATH              write the full per-case result set as JSON
--quiet                  summary only
```

### Exit status

* `0` — every case was handled safely (server stayed alive, no leak, and, under
  `--expect-ssrf-guard`, every private/loopback webhook was rejected).
* `1` — at least one **DANGER**: the server died, hung process-wide, reset,
  returned 5xx, leaked a path/panic, or accepted a webhook it should reject.
* `2` — no server answered at the target address.

Exit `0`/`1` make the probe usable as a CI gate. Verify it in both directions:
against the default (guard-on) server `--expect-ssrf-guard` exits `0`; against a
server started with `A2A_ALLOW_PRIVATE_WEBHOOKS=1` it exits `1` and flags every
`F*` case — a gate that only ever passes proves nothing.

## Categories

| | Focus | Examples |
|---|---|---|
| **A** | parser / framing | truncated JSON, control bytes, empty/whitespace body, wrong `jsonrpc` version, method-as-int, params-as-array, 2000-deep nesting, empty/500-item batch, duplicate keys, 8 MB body vs the 4 MiB cap, missing/bogus `A2A-Version`, lying `Content-Length` |
| **B** | field abuse | path-traversal `taskId`, 1 MB `taskId`, empty `parts`, invalid role, `text` as int, empty part object, lone UTF-16 surrogate, RTL override + NUL, `null` message, unknown top-level fields |
| **C** | state / numeric | unknown / null ids, `pageSize` of `-1` / `2^63` / `2^64` / a float, traversal `pageToken` |
| **D** | task lifecycle | get / cancel / double-cancel / get-after-cancel / resubscribe on a real seeded task |
| **E** | http surface | GET / PUT / DELETE / OPTIONS on the RPC endpoint, `text/plain` content type, unknown path |
| **F** | push-config SSRF | loopback, cloud metadata (`169.254.169.254`), RFC1918, `[::1]`, IPv4-mapped, NAT64, `metadata.internal`, `.local`, `file://`, `gopher://`, userinfo smuggle, **decimal / hex / octal integer** encodings of the metadata IP, CRLF header injection |

`D` and `F` first create one real task (via `SendMessage`, which reaches the
model), because push-config validation and lifecycle transitions only apply to a
task that exists — testing them against a fabricated id would return
`TaskNotFound` and falsely read as "rejected".

## Interpreting a run

Every line prints the liveness verdict, the observed status, the wall time, and
a tag: `jsonrpc-error:<code>` is the good outcome for a hostile input;
`accepted` means the server processed a (valid or leniently-parsed) request.
Two behaviours look alarming but are correct, and the harness is written to
recognise them rather than cry wolf:

* **8 MB body** → the server rejects on the `Content-Length` fast path with a
  structured `-32700` *before* buffering the payload; the harness reads that
  early reply instead of finishing an upload the server has already refused.
* **short body under a large `Content-Length`** → the server correctly keeps
  reading, bounded by its `body_read_timeout`; a `TIMEOUT` with the server still
  answering other clients is the expected result, not a hang.

## History

These harnesses were written to stress the SDK against a live `llama-server`
(Qwen3.5-0.8B, Apache-2.0) before a public release. They found two issues, both
fixed and regression-tested:

* the registration-time webhook filter did not normalise integer/hex/octal IPv4
  encodings, so `http://2852039166/` (== `169.254.169.254`) was stored though
  delivery still blocked it (`probe.py` `F17`–`F19`, and
  `crates/a2a-protocol-server/src/push/sender.rs`);
* the gRPC binding processed a request with no `a2a-version`, while JSON-RPC and
  WebSocket rejected the same request per spec §3.6.2 — a cross-binding
  inconsistency only visible because `probe_grpc.py` hits every binding with
  the same attack (`crates/a2a-protocol-server/src/dispatch/grpc/`).

The full account is in the book: **Testing & Deployment → Adversarial
Testing**.
