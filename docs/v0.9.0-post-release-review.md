# Post-v0.9.0 review

A critical read of this repository after the 0.9.0 release, written against
first-hand measurement rather than against the repository's own claims about
itself. Every number below was produced on this checkout during the review;
where something was *not* verified, it says so.

Two things frame it. The `a2a-protocol-types` crate has passed 20,000 downloads
(25,022 total / 24,268 in the last 90 days, crates.io API, 2026-08-17), so
mistakes here reach people. And since this project started, the A2A project has
published **its own Rust SDK** — `a2aproject/a2a-rs` — which changes what
"complete" has to mean.

## What was verified, and what it showed

| Check | Command | Result |
|---|---|---|
| Workspace build | `cargo build --workspace --all-features` | exit 0 |
| Workspace tests | `cargo test --workspace --all-features` | exit 0 — **2,837 passed, 0 failed, 157 ignored** |
| SLIMRPC binding build | `cargo build --all-targets` in `bindings/` | exit 0 |
| Vendored SLIMRPC spec vs upstream | `scripts/check_slimrpc_spec.sh` | exit 0 — 2 files match |
| Vendored protos | `scripts/check_proto_copies.sh` | exit 0 — 5 files × 4 copies identical |
| File-length ratchet | `scripts/check_file_lengths.sh` | 80 of 409 over 500 lines, all recorded |
| Book `ignore` ratchet | `scripts/check_book_code.sh` | 130 blocks across 21 files, matches baseline |
| API reference names | `scripts/check_api_reference.py` | 116 names, all defined |

The suite is real and it is green. The README said "~2,740 tests"; the measured
figure is 2,837 passing. Stale, and in the conservative direction — corrected in
this branch.

**Panic discipline is genuinely good, and is worth stating because it is the
thing most often wrong in a Rust server SDK.** Excluding `#[cfg(test)]` modules,
`build.rs`, benches, and doc comments, there are **52** `unwrap`/`expect`/`panic!`
sites across all four crates, and the runtime ones are lock-poisoning `expect`s
plus one `signal(SIGHUP)` registration. There are **zero** `TODO`/`FIXME`/`HACK`
markers in `crates/*/src` or `bindings/*/src`. This is not a weak area.

## 1. The thing that changed: there is now an official Rust SDK

`a2aproject/a2a-rs` publishes six crates. `a2a-lf` has **31,655** downloads
against this project's `a2a-protocol-types` at **25,022**. It is not a
side project — it is the A2A project's own.

| | this project | `a2aproject/a2a-rs` |
|---|---|---|
| Bindings | JSON-RPC, REST, **WebSocket**, gRPC, SLIMRPC | JSON-RPC, REST, gRPC, SLIMRPC |
| Server base | raw `hyper` 1.x, Axum optional | `axum` |
| MSRV | **1.93** | **1.85** |
| CLI | — | `a2acli` |
| Card-driven transport selection | four built-in bindings only | `TransportFactory`, SLIMRPC included |
| Conformance evidence | official TCK 92/114 MUST, in-repo runner, ITK, mutation ledger | none published |
| SLIMRPC multicast (`slimrpc-multicast.md`) | **implemented** | not implemented |
| SLIMRPC `Collaborate` (collaborative channel) | **not implemented** | implemented |

Read honestly, this project is ahead on transports, on testing, and on evidence,
and behind on three things that decide adoption:

* **MSRV 1.93 vs 1.85.** Eight minor versions of Rust. This is the single
  largest adoption barrier in the repository, and it is now measurable against a
  direct alternative rather than against a hypothetical conservative user. The
  ROADMAP lists it as an open question; the answer got easier.
* **No CLI.** `a2acli` inspects cards and manages tasks. Evaluating this SDK
  requires writing Rust; evaluating theirs does not.
* **No card-driven transport selection for SLIMRPC.** Theirs resolves a card and
  dials whatever it advertises. Ours requires `with_custom_transport` by hand,
  because `builder/transport_factory.rs` knows four binding constants and has no
  registration hook.

None of these is a defect. All three are the reasons someone picks the other one.

## 2. SLIMRPC: what "complete" actually requires

The binding implements all eleven methods plus multicast, tested across ten
topologies with **37 integration test functions** and real SPIRE. The official
crate's suite is **4 test functions in one topology**. On depth this is not
close.

Reading `spec/slimrpc_v1/slimrpc.md` clause by clause against the
implementation, and against the official crate for comparison:

### 2.1 Service parameters are not transmitted (§3, a MUST)

§3: *"A2A service parameters … **MUST** be transmitted using the SLIMRPC
metadata mechanism"*, with `a2a-version: 1.0` as its own example.

`SlimRpcTransport`'s `metadata_from` forwards `extra_headers` and nothing else,
and `ClientRequest::new()` starts that map empty. Every other client transport
in this workspace injects the version explicitly —
`transport/jsonrpc.rs:199`, `rest/request.rs:101`, `websocket.rs:255`,
`grpc.rs:235`. **SLIMRPC does not.**

The server half matches: `headers_from(ctx)` returns `ctx.metadata()` raw, and
nothing validates a version. Every other binding does — `validate_version_header`
for JSON-RPC and REST, `check_a2a_version` for WebSocket, `validated_metadata`
for gRPC.

Two things make this more than a missing line:

* **An out-of-workspace binding cannot fix the server half.**
  `validate_version_header` is `pub(crate)` and `validated_metadata` is
  `pub(super)`. This is the same shape of problem as the missing
  `EventStream::from_event_channel` that building this binding already
  uncovered: the extension point is incomplete, and reading the signatures does
  not show it.
* **The official crate does not send it either** — checked against
  `a2a-slimrpc` 0.2.4's source. So this is not an interop break between the two
  implementations. It is a §3 MUST that neither satisfies, and the honest
  framing is "unimplemented by both", not "we are behind".

### 2.2 Internal SLIMRPC metadata leaks into the A2A header map

The official crate filters SLIMRPC's own keys — `deadline`, `status-code`,
`rpc-id`, `service`, `method` — before handing metadata to the handler
(`common.rs::is_internal_metadata_key`). Ours does not: `headers_from` returns
`ctx.metadata()` unfiltered, and that map is what feeds `RequestHandler`'s auth
and tenant resolvers. A `HeaderTenantResolver` keyed on a colliding name would
read transport plumbing as an A2A header. Narrow, but it is a correctness gap
with a known-good reference fix.

### 2.3 Address parsing is stricter than the spec's own examples

`SlimName::parse` requires the `slim://` prefix and rejects anything else. But
§2.1 of the same spec presents bare `mydomain/demo/echo_agent` as *the* SLIM
Name form, and the official crate accepts all three of `org/ns/app`,
`slim://org/ns/app`, and `slimrpc://org/ns/app`. A card written by the official
SDK using the bare form is rejected by ours. One `strip_prefix` chain fixes it.

### 2.4 Two spec observations worth recording

* The vendored spec's §1 says the service is `a2a.v1.A2AService`; both
  implementations use `lf.a2a.v1.A2AService`, which is what the ratified
  `a2a.proto` package actually is. The spec text is internally inconsistent with
  its own §4. **Both implementations agree, so there is no interop break** — but
  the repository vendors that spec and says nothing about the discrepancy.
* `scripts/check_slimrpc_spec.sh` compares two named files. It cannot see a
  *new* file appearing upstream. The official crate references a "collaborative
  channel extension spec" that is not in `a2aproject/experimental-cpb-slimrpc`
  at all — so the mechanism by which that binding grows is one this repository's
  drift check is structurally unable to notice.

### 2.5 The binding is outside every supply-chain gate

`bindings/a2a-protocol-slimrpc` is `publish = true`, ships 379 transitive
dependencies including a native C crypto build, and:

* `cargo deny` runs at the workspace root, so **none of those 379 are audited**;
* the `package` job's `cargo package --workspace` cannot see it, so **nothing
  validates that it packages or publishes**;
* it is in no coverage or mutation run.

Its CI job runs fmt, clippy, build, test, and SPIRE. That is good, and it is not
the same as the four workspace crates' gates. For a crate that is published to
users, the audit gap is the one that matters.

## 3. Worst performance: persisted streaming events

Measured on this checkout with a probe written for the review
(`SqliteTaskStore`, fresh database per arm, three interleaved repetitions,
best-of-3 per bucket, release build):

| artifact parts | `save_artifact_delta` | full `save` | ratio |
|---:|---:|---:|---:|
| 100 | 170 µs | 203 µs | 0.84× |
| 300 | 287 µs | 295 µs | 0.97× |
| 500 | 359 µs | 426 µs | 0.84× |
| 1000 | 541 µs | 541 µs | **1.00×** |

Two findings, and the second is the uncomfortable one.

**Persisting one streaming event costs 170–540 µs.** The repository's own CI
benchmark agrees independently — `backpressure_append_volume/sqlite_store_502_events`
is 110.02 ms, or 219 µs/event — and that is against 2.83 ms for the same 502
events in memory, a **39× penalty**. At 200 µs/event, an agent emitting 100
events/second saturates a core at roughly 50 concurrent tasks. This is the
dominant cost of any persistent A2A agent built on this SDK, and SQLite is the
store the documentation recommends first.

**The 0.9.0 "incremental artifact persistence" does not deliver an asymptotic
win.** It is modestly better at small documents — which is where it was tuned,
and the code comments say so — and it converges to exactly the full rewrite by
1000 parts. The cause is visible in `artifact_delta_sql`: the statement is
`UPDATE tasks SET data = json_set(data, '$.artifacts[…].parts[#]', …)`, and
SQLite's `json_set` parses and re-serialises the entire `data` document. The
Rust-side serialisation is saved; the database-side rewrite is not, and it is
the larger half.

This is not a bug — the code does what it says. But "incremental persistence"
reads as an order-of-magnitude claim and the measurement does not support one.
A real fix means normalising parts out of the JSON blob into their own
append-only rows, which is a schema change, not a statement change.

**Second-worst, and less alarming:** `transport_jsonrpc_send/single_message` at
194.8 µs on loopback. That is a full HTTP round trip through hyper, and the
`realistic_interceptor_chain` series shows ten interceptors add only ~8 µs, so
the cost is the stack rather than this SDK's logic. It is not a defect; it is
the number to know before promising throughput.

## 4. Worst developer experience

Ranked by how many people hit it.

1. **MSRV 1.93.** Covered above. It is the first thing that stops an
   organisation from adopting, and it now has a 1.85 alternative.

2. **The Quick Start taught a server you could not ship** — fixed in this
   branch. `serve()` accepts forever and returns only if you drop its future,
   which cancels the accept loop and silently kills in-flight connections.
   `examples/deploy-agent` — the example whose entire subject is deployment —
   had to switch to the Axum adapter for `with_graceful_shutdown`. The path the
   README teaches and the path the production example uses were different
   functions, and nothing said so. `Server::bind(..).serve_with_shutdown(..)`
   now closes it.

3. **No CLI.** Evaluating this SDK means writing Rust and compiling. That is a
   real barrier at the "does this work at all" stage.

4. **Compile time.** A cold `--all-features` workspace build is minutes, and the
   test binaries take longer than the tests. Partly inherent to 16 feature
   combinations; still what a contributor feels first.

5. **Ten feature flags on the umbrella crate**, and the SLIMRPC binding is not
   among them — it cannot be, being out of workspace. `a2a-protocol-sdk` is sold
   as the batteries-included entry point and one binding is unreachable from it.

## 5. What misses the production-ready bar

The framing this repository already uses — *supported* and *verified* are
different claims — applied to the operational surface.

* **~~`serve()` cannot drain.~~ Fixed in this branch.**
* **~~`serve()` has no connection ceiling.~~ Fixed** for the new entry point.
  `serve()` and `serve_with_addr()` still spawn a task per accepted socket with
  no bound; the EMFILE backoff handles the symptom, not the cause.
* **No connection-level timeouts anywhere.** There is an `executor_timeout` for
  agent code and request timeouts on the client, but no header-read timeout and
  no idle timeout on the server. A slowloris connection holds a task
  indefinitely. This is the largest remaining hardening gap and it is not
  in the ROADMAP.
* **`serve()`/`serve_with_addr()` discard `serve_connection`'s result**
  (`let _ = …`). A connection that failed to negotiate and one that served a
  thousand requests are indistinguishable. Inconsistent with this project's own
  "make failure paths observable" work in 0.9.0. The new entry point traces it;
  the old two still do not.
* **`serve_with_addr` spawns and returns no handle** — the accept loop cannot be
  joined or aborted.
* **`panic = "abort"` in the release profile.** For binaries built from this
  workspace, any panic — including a poisoned-lock `expect` — takes down the
  whole process rather than one task. Defensible for a CLI, worth an explicit
  decision for a server, and currently it is a workspace default nobody records
  a reason for.
* **Rate limiting is per-process.** Three replicas mean 3× the configured limit.
  The module says so further down; the summary line said "token-bucket" when the
  implementation is a fixed window — corrected in this branch, because a fixed
  window admits 2× the limit across a boundary and anyone sizing against an
  upstream ceiling needs that from the summary.
* **No sustained-load or soak evidence anywhere in the repository.** Criterion
  measures latency at fixed concurrency for seconds. Nothing measures an hour, a
  leak, or a slow degradation. The SLIMRPC README is admirably explicit that it
  has none; the rest of the repository has none either and does not say so.

## 6. Documentation and GitHub Pages

The book is 11,593 lines across 43 pages, live at a2a-rust.com, with search,
themes, canonical URLs, and a sitemap. Structurally it is in good shape. What is
missing is thematic, and it maps almost exactly onto the headline features:

* **No chapter on multi-tenancy.** `TenantResolver`, `PerTenantConfig`, and four
  tenant-aware stores are a headline feature with no page of their own —
  scattered mentions across `stores.md` and `configuration.md`.
* **No chapter on observability.** Same story for `Metrics` and OpenTelemetry.
* **No chapter on security.** SSRF protection, body limits, CORS, path-traversal
  defence and header-injection prevention are spread across `production.md` and
  the API reference.
* **No troubleshooting or FAQ page at all.** Zero occurrences of either word in
  `book/src/`. For an SDK whose failure modes include "wrong `A2A-Version`
  header", "stream ended without a terminal state", and "SPIFFE handshake never
  completes", this is the highest-value missing page.
* **No upgrade guide.** A 0.x that says minor versions may break should tell
  people how to cross one. The CHANGELOG is 191k and is not that.
* **SLIMRPC is filed under "Building Agents"** rather than a bindings section,
  and its book page carries the only structural entry in the ignore-baseline.
* The examples README table lists six of eight examples — `hello-agent` and
  `deploy-agent` are absent from it.

## 7. Examples still to build

The six measured examples each hit 44/44 method×binding cells, and
`incident-response` runs sixteen production-hardening checks. The coverage
*within* the examples is not the gap. The gaps are whole categories:

* **No example uses SLIMRPC.** The binding is out of workspace, so `examples/`
  cannot depend on it — meaning the binding with the most novel operational
  surface (SPIFFE, multicast, fabric nodes) has zero presence in the place
  readers actually look.
* **`multi-lang-team` has no Rust worker.** Python, JS, Go, Java — and the ITK
  now has an obvious fifth language it does not cover: the official Rust SDK.
  Interop with `a2aproject/a2a-rs` is the single most valuable missing ITK leg,
  and it is missing because the SDK did not exist when the matrix was drawn.
* **No durability example.** Nothing demonstrates an agent restarting and
  resuming a long-running task from a persistent store. `incident-response`
  checks that a task survives a handler swap, which is close but is a check
  rather than a narrative.
* **No failure-injection example.** Nothing shows what an operator sees when the
  store is down, the push endpoint is refusing, or the queue is full. The
  `Metrics` hooks for exactly these were added in 0.9.0 and no example reads
  them under fault.
* **No horizontal-scaling example.** Two replicas behind a load balancer sharing
  a Postgres store is the first architecture anyone deploying will reach for,
  and it is where the per-process rate limiter and in-memory event queues stop
  being adequate. Nothing addresses it.

## 8. What misses the engineering-excellence bar

Little does, and it is worth being precise about which little.

* **`send_message_inner` is 526 lines** — measured, the largest function in the
  codebase, on the hottest path, carrying interceptors, extension and streaming
  checks, id and metadata validation, capacity admission, three-phase stale-token
  eviction, and task creation. Already recorded in `.file-length-baseline` with
  an honest note. It is still the one place where a reviewer cannot hold the
  whole behaviour in their head.
* **80 of 409 source files exceed the 500-line guideline.** Ratcheted, so it can
  only shrink — but a fifth of the tree is over the bar the project set.
* **`mutants.toml` was never read by cargo-mutants** (wrong path), so every
  published mutation score includes generated protobuf mutants and ran with a
  328 s budget rather than the 300 s cap the file claims. The ROADMAP documents
  this thoroughly and defers it. It is the one place where a headline number
  measures something other than what it says it measures.
* **Two doc defects found by reading**, both corrected here: the rate-limiter
  algorithm and two stale README figures. Both were in the first line a reader
  sees.

Against that: zero TODOs, 52 panic sites in non-test code across 140k lines,
`#![forbid(unsafe_code)]` everywhere, every gate proven able to fail by
injection, and a ROADMAP that documents its own measurement errors including one
that was wrong by an order of magnitude in the *optimistic* direction. That
combination is rare.

## 9. What I am least confident in

Stated plainly, because the rest of this document is assertive.

1. **Absolute performance numbers.** The SQLite figures were taken on a shared
   cloud VM with unknown I/O characteristics. The *relative* comparison
   (delta vs full save) is sound because the arms were interleaved on fresh
   databases; the absolute µs are indicative. That CI's independent 219 µs/event
   lands inside my 170–540 µs range is corroboration, not proof.
2. **The claim that `json_set` is the cause.** I read the generated SQL and the
   growth curve matches, but I did not profile SQLite itself. The mechanism is
   inferred from two consistent observations, not measured directly.
3. **The official SDK comparison.** Built from its published README, its
   `a2a-slimrpc` 0.2.4 source, and crates.io metadata. I did not build or run it.
   Feature claims from a README are not verified behaviour — the same standard
   this project applies to itself.
4. **Download counts as adoption.** 25,022 is real, but crates.io counts include
   CI, mirrors, and docs.rs builds. It is evidence of reach, not of production
   use, and the gap between those two is unknown.
5. **The 157 ignored tests.** I confirmed they are database-gated and that CI
   provides the service; I did not run them here.
6. **Anything about sustained behaviour.** No soak test was run, by me or by
   this repository, ever. Every statement about stability under hours of load is
   unevidenced — including the optimistic ones.

## 10. What fails the "proudly call it production ready" bar

The parts I would not defend without qualification, in order:

1. **Connection-level timeouts do not exist.** A server with no header-read or
   idle timeout is not one I would put on a public interface without a proxy in
   front, and the documentation does not say to.
2. **No soak evidence.** "Production ready" implies someone ran it for longer
   than a benchmark. Nobody has.
3. **Horizontal scaling is undemonstrated and partly unsupported.** The rate
   limiter is per-process and the event queues are in-memory. A second replica
   changes behaviour in ways nothing documents.
4. **The SLIMRPC binding is published without dependency auditing.** 379
   transitive dependencies, including native crypto, reaching users through a
   crate that `cargo deny` never sees.
5. **Persisted-event throughput.** 39× slower than memory, with the headline
   optimisation not delivering asymptotically. Fine for a control-plane agent,
   not fine for a high-rate streaming one, and nothing tells you which you have.

Everything else — the protocol surface, the conformance evidence, the testing
discipline, the honesty of the ROADMAP — I would defend as-is.

## 11. What I would do differently

* **Decide the MSRV against 1.85, not against a hypothetical.** It is now a
  competitive fact.
* **Ship a CLI.** It is the cheapest adoption unlock available and the official
  SDK has already established the expectation.
* **Bring SLIMRPC inside the gates that matter.** Not the workspace — that
  reasoning is sound — but `cargo deny` and `cargo package` should see it. A
  separate `deny.toml` in the binding directory and a `--dry-run` package step
  are both small.
* **Add the official Rust SDK to the ITK.** It is the highest-value interop leg
  available and the matrix already has the shape for it.
* **Stop optimising SQLite statements and change the schema**, or document the
  per-event cost as a hard number in the stores chapter so readers can size
  against it. The current position — an optimisation whose name promises more
  than it delivers, and no published per-event figure — is the worst of both.
* **Write the troubleshooting page before the next feature.** It is the largest
  gap per hour of work in the entire repository.

# Addendum: what this branch changed

Written after the review above, against the same standard — every claim below
was run on this checkout, and the corrections are corrections of *my own*
findings where measuring more carefully contradicted them.

## Two things I reported that were wrong, both in the optimistic direction

**The SQLite delta path was not converging to parity — it had become a
pessimisation.** The review said delta/save reached 1.00× at 1,000 parts. Run
through `SqliteTaskStore` itself rather than through a hand-written probe, it
crosses 1.0 and keeps going: **1.39× at 1,000 parts and 1.48× at 3,000**. Past
roughly 300 parts, the incremental path was slower than rewriting the whole
record, because it paid a `json_set` parse of the document on top of everything
a full save does. Appended parts now go to an append-only side table, and the
append is flat at ~130 µs from ten parts to three thousand.

**The header-read timeout was not missing — it was silently disabled.** The
review said there were no connection-level timeouts. Hyper *has* one and
defaults it to 30 seconds; it applies only when a `Timer` is installed on the
connection builder, and no server here installed one, so `Time::check` logged
`timeout \`header_read_timeout\` has default, but no timer set` and returned
`None`. Every component was correct and the composition disabled the defence.
That is a worse defect than the one I described, and a different kind: not an
absent feature but an absent line, invisible in every type signature involved.

## Fixed

| Finding | Status |
|---|---|
| SLIMRPC sends no `a2a-version` (§3 MUST) | Fixed — and `validate_version_metadata` is now public, so the server half is fixable from outside the workspace at all |
| SLIMRPC leaks transport keys into A2A headers | Fixed, case-insensitively, taking two keys from `slim_rpc` itself |
| `SlimName::parse` rejects the spec's own bare form | Fixed — bare, `slim://` and `slimrpc://` all resolve to one name |
| 379 published dependencies unaudited | Fixed — `cargo deny` and `cargo package` now run on the binding. **Advisories: clean** |
| No header-read timeout | Fixed — the `Timer` is installed and the timeout is configurable |
| No idle timeout | Fixed — enforced at the socket, counting traffic in both directions so SSE survives |
| Incremental persistence delivers no asymptotic win | Fixed — append is now O(1) in document size |
| Nothing has ever been soak-tested | Fixed — 562,690 requests, 17.0 bytes/request, p95 flat; nightly in CI |

## Where the tests were the problem, not the code

Four tests passed against a defect they existed to catch, and each was found by
injection rather than by review:

* The slowloris test passed with the `Timer` removed — because
  `with_idle_timeout(None)` was a `Duration::MAX` sentinel, `Instant::now() +
  Duration::MAX` panicked in the connection task, and the peer saw a reset in
  94 ms. The disabled path was broken *and* the test passed because of it.
* The same test asserted an outcome ("the read completed") where the property
  is a reason. A connection dropped by a panicking task completes the read too.
* The SSE test never read, so it never reached the deadline check, and passed
  with writes not counting as activity at all.
* Nothing asserted the artifact journal is ever emptied. `splice` skips
  positions the document already holds, so a `save` that failed to clear it
  returns correct tasks forever while the table grows without limit — invisible
  to any test that only checks what comes back.

## Still open

* ~~**Horizontal scaling.**~~ **Closed, and it was mostly not what I said it
  was.** Measured with two handlers over one PostgreSQL
  (`tests/multi_replica.rs`): task visibility crosses replicas, and so does
  subscription *termination* — the reattach hook polls the shared store, so
  §3.1.6 holds across replicas, which I had assumed rather than checked.
  Intermediate events do not cross, which is architectural and now pinned by a
  test. The one real defect was the rate limiter, and
  `RateLimitInterceptor::with_shared_counter` closes it. Two replicas under
  sustained load is now measured too — 64,642 request pairs, 0 failures, 0
  cross-replica misses, 19.2 bytes/pair, p95 flat at 1.04x. See Addendum 3 for
  the two findings that run turned up.
* **MSRV 1.93 against the official SDK's 1.85.** A decision, not a defect.
* **No CLI.**
* **No troubleshooting page**, and no chapter for multi-tenancy, observability
  or security.
* **No example uses SLIMRPC**, and `multi-lang-team` still has no Rust worker.
* **`send_message_inner` is 526 lines.**
* **`mutants.toml` is still at the wrong path.**

# Addendum 2: the horizontal-scaling gap

Called out in the first addendum as "the largest remaining gap". Measured, it
was four separate questions with four different answers, and only one of them
was a defect.

| Claim | Measured | |
|---|---|---|
| A task created on replica A is readable on B | **works** | the store holds it |
| `GetTask` / `ListTasks` span replicas | **works** | same |
| A subscription on B terminates when the task finishes on A | **works** | reattach hook polls the store; §3.1.6 holds across replicas |
| B sees A's intermediate events | **does not** | queues are per-process; architectural |
| The configured rate limit is the deployment's | **did not** | each replica admitted the full rate |

I had reported this as one gap. Three quarters of it already worked, and the
part about subscriptions being spec-compliant across replicas was something I
assumed rather than verified in either direction.

## The fix, and what it costs

`RateLimitCounter` is a one-method trait; `PostgresRateLimitCounter` implements
it with a single atomic `INSERT .. ON CONFLICT DO UPDATE .. RETURNING`. Two
limiters sharing one now admit 5 where they used to admit 10.

The cost is not small and is documented rather than buried:

| Counter | Per request |
|---|---:|
| In-process (default) | 0.2 µs |
| `PostgresRateLimitCounter` | 232 µs |
| The same on a durable pool | 598 µs |

A whole JSON-RPC request through this server measures ~195 µs on the same
machine, so a shared counter roughly doubles a request. The 598 → 232 µs comes
from running the counter's own pool with `synchronous_commit = off` — correct
for a counter describing a 60-second window, and deliberately *not* applied to a
pool passed in via `from_pool`, which is usually the task store's.

When the counter is unreachable the limiter counts locally, so the failure mode
is the per-process behaviour the deployment already had — not an outage, and not
an open door.

## ~~Finding~~ Fixed: `caller_identity` was never set by anything

The rate limiter documents `CallContext::caller_identity` as its first choice of
caller key, "set by authentication interceptors". Nothing set it:

* `ServerInterceptor::before` takes `&CallContext` — an interceptor
  *structurally could not* mutate one;
* no dispatcher constructed a context with an identity;
* `with_caller_identity` had no caller outside tests.

So every caller shared the `"anonymous"` bucket unless `trusted_proxy_hops` was
configured with an `x-forwarded-for` header present. **Per-caller rate limiting
was not per-caller**, and one noisy client spent everyone's budget. It went
unnoticed because every rate-limit test set the identity by hand on a
`CallContext` it had built itself.

The `JwtAuthInterceptor` had already run into this and left a note — it
computed a validated principal and threw it away, `map(|_principal| ())`, with
a comment saying the principal "is available should a future `CallContext` gain
a slot for it". That slot is the fix.

`CallContext::caller_identity` is now a `OnceLock<String>` with
`set_caller_identity(&self, ..)`, so the component that knows who the caller is
can say so through the shared reference it actually has. Write-once rather than
a mutex because identity is established once; two interceptors disagreeing is a
misconfiguration, and the first answer now sticks instead of the last one
silently winning.

Three interceptors supply one. `JwtAuthInterceptor` records the validated `sub`,
which closes its own comment. `ApiKeyAuthInterceptor` and
`BearerTokenAuthInterceptor` record a label when built with
`with_labelled_keys` / `with_labelled_tokens`.

The label is supplied rather than derived from the credential, deliberately: a
caller key reaches a shared rate-limit table, and can reach logs and metrics. A
bearer token belongs in none of those, so hashing it — the obvious shortcut —
would have put credential-derived material in all three.

One ordering requirement falls out, and it fails silently: the chain runs
interceptors in registration order over one context, so a limiter registered
before authentication reads an identity nothing has set yet and buckets every
caller together. Documented on both the module and the struct.

Verified under load: the two-replica soak now authenticates each of its eight
workers with its own labelled key rather than working around the gap with
`x-forwarded-for`, and the counter table holds eight keys across 63,339 request
pairs.

and `PostgresTaskStore` has no capacity eviction — both correct decisions — so
a deployment needs a retention policy it has to supply itself. Nothing in the

# Addendum 4: a flake I wrote, and a CI setting that hid where it was

## The failure

`Test (1.93, macos-latest)` went red on

```
byte 2 should arrive, got: connection idle for more than 75s; closing to
release the task and descriptor
```

The peer had written that byte 15 virtual seconds inside the window, and the
same test had passed on Linux and Windows, on both toolchains, on every run
before it — including 300 consecutive local runs afterwards. It is my own test,
added with the connection timeouts in `b27d400`, so this is a flake the branch
introduced and got away with once.

## Why paused time and a real socket do not mix

The module claimed `start_paused` made these tests immune to a loaded runner.
That is true of the *timers* and false of the *transport*, and the difference
is in tokio's own auto-advance (`runtime/time/mod.rs`, `park_thread_timeout`):

```rust
self.park.park_timeout(rt_handle, Duration::from_secs(0));
if !handle.did_wake() {
    clock.advance(duration);
}
```

The runtime polls the I/O driver with a zero timeout and then jumps the clock to
the next timer **regardless of what that poll found** — `did_wake` belongs to
the *time* handle, so dispatching a socket readiness event does not stop the
advance. A peer's `write` reaching the kernel and the reader learning the socket
is readable are two different moments, and the virtual clock is free to cross
the idle deadline in between. When it does, the reader polls the socket
(Pending, because readiness has not arrived), polls the deadline (expired), and
reports the connection idle. On epoll the event was always there in time; on
kqueue, once, it was not.

The fix is `tokio::io::duplex`, which removes the gap rather than narrowing it:
a write wakes the reader's waker from inside `poll_write`, so the reading task
is on the run queue before the scheduler can consider parking. Five of the six
tests moved; the sixth asks whether `is_write_vectored` is delegated, which only
a real socket can answer, and it does not pause time.

Widening the window instead — a 300-second idle allowance against 60-second
writes — would have made the race rarer and left it in place. A test whose
failure mode is indistinguishable from the defect it exists to catch is worse
than no test, because the first response to it is to doubt the code.

## A sixth test that was the problem, not the code

`end_of_stream_reads_as_eof_not_activity` asserted only the EOF half of its own
name. Making EOF re-arm the timer — the exact defect the guard in `poll_read`
exists to prevent — changed nothing that test could see, because at this layer a
re-armed timer has no observable effect on a read that already returned zero. It
now reads the deadline directly, before and after, and the injection that
proves it is in the set below.

All four gates are proven able to fail:

|---|---|

## The semver gate said it was advisory. It has been blocking since 0.7.0

The `cargo-semver-checks` job carried the claim twice — once in its header
("this reports rather than hard-fails until the first 1.0"), once inline beside
`feature-group`, a key that selects features and has nothing to do with
blocking. Neither was implemented. There is no `continue-on-error` in the job,
so every break it found has been a hard failure for as long as the comment has
denied it.

The fix is the comment, not the behaviour, because the premise does not survive
being run. The stated reason for wanting it soft — "on a 0.x baseline a MINOR
bump is allowed to break" — describes a rule cargo-semver-checks already
applies. Measured with 0.50.0 against `a2a-protocol-types`, renaming

|---|---|---|
| version unchanged, no break | 0 | no semver update required |
| version unchanged, break present | 100 | semver requires new major version |

The last thing neither local harness could see. `gates_for_jobs` read

### Three bugs in the above, all mine, all found by testing rather than reading

**The quoting.** gsub applies its own backslash rules on top of the string
literal, and the two layers together turned one backslash into six. Rebuilt a
character at a time.

**The guard that checked nothing.** `require_known_skips` iterated
`printf '%s' "$SKIP_STEPS" | tr '|' '\n'` with `while read`. No trailing
newline means `read` returns non-zero on the final line, so the body never ran
for the last alternative — and with a single exemption, that is every
alternative. The guard executed and verified nothing. Found by handing it a
deliberately stale pattern and watching it pass.

**Folded scalars.** The rule matched `run: [|>]` and treated both alike. YAML
folds `>` by joining lines with spaces, so `run: >` / `echo one` / `two` means
`echo one two`; the parser would have emitted two commands, the second of which
does not exist. Confirmed against PyYAML rather than assumed. Folding is
implemented now — see below; the first fix for this was a refusal, which was
the wrong shape of answer.

## Folding, implemented rather than refused

The first response to the folded-scalar bug was to make `gates_for_jobs` refuse
`run: >` and say so. That is defensible — a gate running the wrong command is
worse than a missing one — but it is still a hole with a sign on it, and the
sign said "someone else decide". So `>` is now folded properly:

* a break between two ordinary lines folds to a single space;
* empty lines are not folded away — k empty lines between content become k
  newlines, and the fold-space is dropped;
* a **more-indented** line is kept literally, and the breaks on either side of
  it stay newlines;
* an explicit indentation indicator (`>2`, `|2`) sets the block indent instead
  of inferring it from the first non-empty line, which is the case it exists
  for.

Chomping (`-`, `+`) is parsed and deliberately not acted on: it changes only
how many line breaks end the scalar, and a trailing newline cannot change what
a shell command does. Said out loud here rather than left as an accident.

The more-indented rule cost a second bug. Getting it right for a bare indented
continuation is easy; what is not obvious is that a blank line *before* one
contributes its newline **and** the unfoldable break survives — one blank line
before an indented continuation is two newlines, not one. That was wrong in the
first implementation and neither reading the spec nor reading the code found
it.

What found it was `scripts/check_block_scalars.py`, which is now a CI gate: 22
block-scalar shapes, each parsed by the awk and by PyYAML, compared. It is a
differential test rather than a table of expected strings on purpose — the
expectations come from an implementation that is already right, so the test
cannot inherit the author's misreading, which is exactly how the bug survived
being written and reviewed.

`bash` decodes the `$'...'` quoting in that check rather than the checker
re-implementing it, so the emitter is tested against the shell that will
actually run it and not against a second copy of its own logic.

Proven able to fail, by widening the fold separator to two spaces in
`ci_gates.sh` and watching every folded case go red: `1 proven, 0 unproven`.
The injection breaks folding rather than the checker, because the gate exists
to notice a parser regression.

## The tasks table: settled

I called this an operator decision four times and left it. That was half right
— the *interval* is the operator's, and it has legal inputs as often as
engineering ones — but "we have no mechanism and no stated default" is not a
policy, and calling it one was a way of not doing the work.

The finding, once I looked properly, was not the one I had been describing.
The SDK does have task retention: `TaskStoreConfig` defaults to a one-hour TTL
and a 10,000-task cap, and `InMemoryTaskStore` honours both. What it does not
have is any connection between that config and the persistent stores —
`SqliteTaskStore::new` and `PostgresTaskStore::new` take a URL and nothing
else, and never read it. So the default in-process deployment forgets a task an
hour after it finishes, the durable deployment keeps it forever, and neither
behaviour was written down anywhere an operator would look. **The divergence
was the defect**, not the growth.

### The decision

**A persistent store deletes nothing unless asked. `purge_expired` is how you
ask.**

Forgetting is right for a cache and wrong for a database. A library that
quietly deleted rows from an operator's PostgreSQL would be a far worse
surprise than one that grows. So the default stands, is now stated in the
module docs, in the deployment chapter and in the type itself, and the
mechanism exists for any other answer.

Not wired to a timer inside the store, deliberately: a sweep that fires on its
own fires during your traffic peak, and the store does not know when that is.

### How fast it actually grows

The page said "grows without bound" and left the reader to guess whether that
meant next week or next decade. Measured, for a completed task with a
two-message history and no artifacts, including the indexes the store creates:

| store | bytes/row | 1M tasks |
|---|---|---|
| PostgreSQL 16.13 | 826 | 0.77 GiB |
| `SQLite` | 781 | 0.73 GiB |

Under a gigabyte per million completed tasks. The answer to "is this urgent" is
volume, not time — and now it is a number rather than an adjective.

### What the implementation had to get right

*Only terminal tasks.* `Completed`, `Failed`, `Canceled`, `Rejected`. A task in
`InputRequired` is a workflow waiting on a human, not a leak, and is never
eligible at any age. The in-memory store *does* evict non-terminal tasks under
capacity pressure, because RAM is a hard bound; disk is not.

*`rowid`, not `id`.* `tenant_tasks` is keyed on `(tenant_id, id)`, so the same
task id exists under every tenant. `DELETE ... WHERE id IN (...)` reads
correctly and would have taken one tenant's expired task **and every other
tenant's task of the same name** — silent cross-tenant data loss, triggered
only once two tenants happened to pick the same id. There is a test for exactly
that, on both backends.

*The batch is chosen inside the `DELETE`.* A select-then-bind-back-the-ids
design would hit SQLite's variable limit (999 before 3.32) at precisely the
batch sizes someone would reach for on a first sweep through years of backlog.
A `rowid`/`ctid` subquery keeps the bound parameters at six however large the
batch.

*The clock is the database's.* `strftime('now', ?)` and `now() - $2::interval`,
not a cutoff formatted by the caller: a host running fast would otherwise
delete work younger than the policy allows.

*Journal orphans.* `task_artifact_appends` has `ON DELETE CASCADE`, and
`journal.rs` already records that `from_pool` cannot assume a caller's pool has
`foreign_keys=ON`. So the sweep clears orphans explicitly. Both branches are
tested — with the pragma on, the cascade takes them and the sweep reports
**zero**, which is the healthy reading; with it off, the sweep reclaims them
and says so.

### Three things the work surfaced that I had not expected

**`TaskState` is `#[non_exhaustive]`**, so no downstream crate can match it
exhaustively — which meant my first version of the terminal-state list was a
hand-written array that would keep compiling, and keep looking right, after a
new terminal state was added that it did not mention. Fixed by adding
`TaskState::ALL` to the types crate with a guard that lives where
exhaustiveness is enforceable: an exhaustive `match` assigning each variant an
index, and an array sized by `ALL` that panics if a variant has an index but no
entry. Adding a variant now fails to compile, and adding it to the match
without adding it to `ALL` fails the test.

**`journal_append` never touches the `tasks` row.** Not `state`, not
`updated_at`. That is correct for the delta optimisation — the document is
reconstructed by splicing — and it means a terminal state reached *via* an
append would leave a stale `state` column that both `list(state=…)` and this
sweep would read. It cannot happen on the real path, because the status
transition that makes a task terminal is a full `save`. Worth knowing rather
than discovering.

**The book gate caught an API mistake, not a prose one.** `purge_expired`
first returned `Result<_, sqlx::Error>`, so the doctest for the deployment page
failed to compile for want of `sqlx` — which is the point: every other store
method returns `A2aResult`, and mine was leaking the driver's error type into
callers' signatures. The gate that compiles the book found an API design
problem that no test of mine was looking for.

Verified: 12 `SQLite` retention tests, 3 against a live PostgreSQL 16.13, the
full 26-test ignored postgres suite and the 6-test multi-replica suite still
green, `cargo test --workspace --all-features` 2,906 passed, default 2,898,
clippy clean on both feature sets, and the book's own doctest for the new API
compiles.

# Addendum 5: three failures of one kind, and a gate that does not run on push

The retention work landed in three commits, and two of them exist only because
the first was wrong. All three failures were the same mistake wearing different
clothes, and the mistake was in how I verified, not in what I wrote.

## The class: I checked two points on an eleven-point matrix

`RUSTFLAGS: -D warnings` is set once, at the top of `ci.yml`, and applies to
every job. Fifteen jobs went red on the first push because
`terminal_state_labels` and `effective_batch_size` are crate-internal with only
feature-gated callers: with no backend enabled they are dead code, and dead code
is an error under that flag. The part I had not internalised is that the flag
applies to `a2a-protocol-server` when it is built *as a dependency* — which is
why the failures included `cargo clippy -p a2a-protocol-client` and the SLIMRPC
binding, neither of which mentions retention.

The second failure was the same shape one layer up: the module doc example named
`SqliteTaskStore`, and this crate has no default features, so the doctest failed
to compile in every configuration that does not ask for a backend. Both
configurations I had tried by hand happened to enable one.

`scripts/preflight.sh --full` found that second one before CI reported it. I had
built most of that script earlier in this branch specifically to run CI's
commands with CI's environment, and then did not run it before pushing. It works;
I did not use it.

## What `cargo package` actually resolves, and why it matters here

The third failure is the one worth keeping, because nothing about it is
guessable from the source.

`cargo package` strips path dependencies when it builds the tarball, then
verifies that tarball against the **registry**. The verification log says so if
you read the line rather than skim it:

```
Verifying a2a-protocol-server v0.9.0
   Compiling a2a-protocol-types v0.9.0                     <- no path: crates.io
   Compiling a2a-protocol-server v0.9.0 (/…/target/package/…)
```

So the packaged server compiles against **published** `a2a-protocol-types`
0.9.0, which does not contain the `TaskState::ALL` this branch adds. The general
rule: *a new cross-crate API cannot be consumed by library code in the same
release cycle that introduces it.* `--workspace` packaging does not rescue this
when the sibling version is already published — cargo takes the registry copy.
The gate would have stayed red on every PR until a version bump.

The fix keeps the guard and drops the dependency: `cargo package` builds the
library and not the tests, so a `#[cfg(test)]` reference to `TaskState::ALL`
compiles against the workspace copy, costs nothing at packaging time, and still
fails the moment `TERMINAL_STATES` stops agreeing with `is_terminal()`.

### Correction to Addendum 4

Addendum 4 says the hand-written terminal-state list was "fixed by adding
`TaskState::ALL` to the types crate". That describes the guard inside the types
crate, which still stands. It also implies the *server* derives its list from
`ALL`, and that is no longer true: the server keeps a local `TERMINAL_STATES`
and the agreement is asserted in a test, for the packaging reason above.

## A gate that does not run on push

Twenty-two CI jobs were green on the final push, and the branch would still have
failed on opening a pull request. `dco.yml` triggers on `pull_request` only, so
nothing about a green push tells you anything about it.

It checks two things, and this branch failed both on 13 of its 28 commits: the
author must not be a tool identity (`noreply@anthropic.com` is named explicitly
in the workflow), and there must be a `Signed-off-by` trailer matching the
author. The session's git identity had drifted partway through the branch —
commits up to `fix(server): make per-caller rate limiting actually per-caller`
are authored correctly and signed off, everything after is not. PROVENANCE.md
§3.2 documents the convention and the exact `git config` to set; the workflow
prints the exact rebase to repair it.

Repaired by re-authoring the affected commits and normalising the assistant
trailer to the `Co-Authored-By: Claude <noreply@anthropic.com>` form §3.2
documents — which is also main's dominant form, 47 commits to 7. The tree is
byte-identical before and after; only authorship and trailers changed.

**For anyone picking this up: a green push is not a green PR.** `dco.yml` and
the semver gate behave differently on the two events. Check the workflow
triggers before believing a push.

### 1. (settled — I was right, and it was worse than I expected) The event queue's `write_timeout` did nothing

**Blast radius:** every streaming agent using the persistent path, which is the
default for `SendStreamingMessage`. **Likelihood before measuring:** high — a
`#[allow(dead_code)]` on a field whose name promises a guarantee.

**The test that would settle it:** fill the persistence channel, then time a
write. MEASURED, probe run 2026-08-19 against `main`:

```
BLOCKED after 1024 writes in 207.935674ms
RESULT: write() STILL blocked after 5s+3s (timeout NOT honoured)
```

`DEFAULT_WRITE_TIMEOUT` is public and 5 seconds. `new_in_memory_queue_with_options`
takes it as a parameter. `EventQueueManager` prints it in `Debug`. It was applied
by nothing. The persistence channel is a bounded `mpsc` (capacity
`max(capacity*16, 1024)`) and `send().await` on a full bounded mpsc waits with no
deadline, so a stalled background processor parked the executor **indefinitely,
with no metric and no trace line**. Fixed in this branch; the two new tests fail
in 2.01s against the pre-fix code and pass after (proof run below, Q6).

Why it survived: the doc comment on `DEFAULT_WRITE_TIMEOUT` read *"Broadcast
sends are non-blocking, so this value is not actively used for backpressure."*
That sentence is true about the broadcast channel and irrelevant to the one that
blocks. The reasoning was applied to the wrong channel.

## Q4 — Worst performance

### The realistic worst path: push-notification fan-out, and it is not in the benchmark suite

**MEASURED**, from a test written for this review
(`configs_the_deadline_never_reaches_are_counted_as_skipped`), run at the
**shipped defaults** — `max_push_configs_per_task = 100`,
`push_delivery_timeout = 5s`, per-event budget 30s (hardcoded,
`push_delivery/mod.rs`):

```
delivered = 6      skipped = 94
```

Six of a hundred configured webhooks receive each event. The other 94 are not
contacted at all. The arithmetic is exactly:

```
configs_reached == min(len, budget / push_delivery_timeout)
```

Three things make this the worst realistic path rather than a contrived one:

1. **Delivery is sequential.** OBSERVED, `push_delivery/mod.rs`: a `for` loop
   with an `await` per config. A `tokio::sync::Semaphore::new(16)` was
   constructed per event under a comment describing it as a cap on "hundreds of
   concurrent HTTP requests" — a mitigation for a shape this loop has never had.
   Its own neighbouring comment admitted "deliveries are currently sequential".
   Removed in this branch.
2. **The shortfall was invisible.** The only report was one `trace_warn!`, and
   `trace_warn!` expands to nothing without the non-default `tracing` feature.
   In the build most people run, 94 webhooks going unnotified produced *zero*
   observable output. Fixed: each skipped config now increments
   `push_outcome::SKIPPED`.
3. **It back-pressures onto the executor.** `deliver_push_bg` is awaited inline
   in the per-task background processor, which is also what drains the
   persistence channel. A slow webhook estate therefore stops task persistence
   for that task — and until this branch, once the 1,024-deep channel filled,
   `EventQueueWriter::write` blocked **forever** (Q2.1).

Blast radius is per task, not per process: the processor is spawned per task
(OBSERVED, `event_processing/background/mod.rs`). That is the right design and it
is why this is a bad day rather than an outage.

### Where the benchmark harness measures the wrong thing

**MEASURED**: the suite has 15 bench files and 77 benchmark groups. Two are named
for push notifications — `enterprise/push_config` and `production/push_config`.
Both measure **config CRUD**: `bench_push_config_roundtrip`
(`benches/benches/production_scenarios.rs:363`) times
`client → server → store → response` for `set_push_config`.

**Nothing in the suite times a push *delivery*.** The one push-notification path
with a 30-second budget, a hardcoded fan-out ceiling and an outward HTTP call is
unmeasured, while the CRUD call that writes a row is measured twice.

And the harness **says so**, which is more interesting than if it did not. Both
files carry a "What this does NOT measure" section naming "External webhook
delivery latency (network I/O)" (`enterprise_scenarios.rs:31`) and "Actual
webhook delivery (external HTTP calls)" (`production_scenarios.rs:36`), and
`benches/src/executor.rs:281` provides a `NoopPushSender` specifically so the
benchmarks can have push enabled without delivering anything. That is honest
harness design: the exclusion is deliberate, declared, and defensible — a
criterion benchmark cannot usefully time somebody else's HTTP endpoint.

So the finding is not "the harness lies". It is that **the declared exclusion
and the operational cliff are the same path, and nothing else covers it
either** — not a test, not a soak, not a metric, until this branch. A stated
exclusion is a promise that something else will look; here nothing did. The
right instrument is not criterion. It is a test with a controllable sink and an
assertion about *counts*, which is what
`configs_the_deadline_never_reaches_are_counted_as_skipped` now is.

Second, smaller instance: `backpressure/*` measures queue *volume*
(`sqlite_store_502_events`) but not queue *saturation* — no benchmark or test
filled the persistence channel before this branch, which is why the unbounded
block survived.

### Re-stating §3 honestly

§3 of this document reports 170–540 µs per persisted streaming event on SQLite
and a 39× penalty against memory. **I did not re-measure it**, and it is
therefore UNVERIFIED at `4ddb7ab`. It remains the largest performance claim in
this file. Re-running its probe is backlog **B9**.

## Q6 — What misses the engineering-excellence bar?

### A gate that was red on `main`, on a commit CI never ran

This is the most serious finding in this addendum, and it is a process defect
rather than a code one. MEASURED, in this order:

```
$ git log --oneline -1 main
4ddb7ab chore: update benchmark results

$ ./scripts/check_benchmark_prose.sh ; echo $?
check_benchmark_prose: benchmarks.md prose disagrees with its own tables
  DRIFT  prose does not contain '22.8%' (64B->16KB latency increase)
  DRIFT  prose does not contain '128.7 µs (39.8%)' (connection-reuse saving)
1

$ grep -n check_benchmark_prose .github/workflows/ci.yml
100:        run: ./scripts/check_benchmark_prose.sh
```

and the run list for `ci.yml` on `main` (GitHub Actions API): the newest run is
`6c926a77`, the PR #111 merge. **There is no CI run for `4ddb7ab`.**

The cause, OBSERVED: `benchmarks.yml:57` checks out with
`token: ${{ secrets.GITHUB_TOKEN }}` and `:139` pushes to `main`. GitHub does
not trigger workflow runs for pushes authenticated with `GITHUB_TOKEN` — by
design, to stop recursion. So **every** "chore: update benchmark results"
commit lands on `main` without CI, and the one job that rewrites
`benchmarks.md` is the one job that never checks it.

This is the same shape as Addendum 5's `dco.yml` finding — *a gate whose trigger
does not cover the event that breaks it* — and it is the second instance. That
makes it a class, not an accident.

The two interlock, which is worth stating. MEASURED, by running `dco.yml`'s
own check locally over `origin/main`'s history: `4ddb7ab` — the bot commit that
is `main`'s HEAD — **fails its authorship rule**, because
`41898282+github-actions[bot]@users.noreply.github.com` matches `NON_HUMAN`. It
never fails in practice for exactly the same reason `ci.yml` never runs: the
commit reaches `main` by direct push and so is never inside a
`pull_request.base.sha..head.sha` range. Two independent gates, both correct,
both structurally unable to see the same commits.

**And the gate could not be satisfied by its own remedy.** Its failure message
says "Regenerate it with `cargo bench` + `generate_book_page.sh`". Regenerating
would not have fixed it, because (MEASURED, by reproducing both derivations):

```
$ python3 -c "print(f'{((241.4-196.5)/196.5)*100:.1f}%')"   # from the rounded table
22.8%
$ python3 -c "print(f'{(323.0-194.3):.1f} µs')"             # from the rounded table
128.7 µs
```

The generator computes the prose from full-precision `estimates.json`
(`extract_median_ns`) and got 22.9% and 128.6 µs. The checker recomputes from
the **rounded table on the page** and gets 22.8% and 128.7 µs. Both are
arithmetically right; they differ only by the rounding the table itself
introduces. A regenerate reproduces the full-precision answer every time, so the
gate stays red on correct output.

Fixed in this branch, three ways, because each addresses a different half:

1. `generate_book_page.sh` gains `extract_median_ns_as_tabled`, which quantises
   to exactly the precision `extract_median` prints, and `derive_pct_increase` /
   `derive_saving` now use it. Prose and tables agree **by construction**, which
   is the property the checker is entitled to assume.
2. The three stale prose figures are corrected by hand to the values the rounded
   tables imply — the same values the fixed generator will now produce. Editing
   this page by hand is normally the wrong move; here the correct value is
   *defined by* the table, and the alternative was leaving `main` red until the
   next bench run. `./scripts/check_benchmark_prose.sh` now exits 0.
3. `benchmarks.yml` runs `./scripts/check_benchmark_prose.sh` after generating
   and before committing, so the job that writes the file is the job that stops
   a bad one reaching `main`. Registered in
   `scripts/prove_workflow_gates_fail.py` as `Exempt` — the script is already
   proven able to fail by `scripts/prove_gates_fail.sh:312` from its `ci.yml`
   call site, and two harnesses claiming one gate is what that file's own header
   rules out. Without registering it the step would have been **invisible** to
   the prover: its body is a bare script call with no literal `exit`, so
   `EXPLICIT_FAIL` does not match and it is not auto-selected. Prover now reports
   `20 proven, 0 unproven, 14 exempt, 0 not selected (of 34 registered)`.

## Q11 — What should be done differently

### My own working method, and where it failed today

Addendum 5 diagnosed the previous session's three CI failures as one class:
*checking two points on an eleven-point matrix while a purpose-built preflight
script sat unused*. I read that before starting, and **I reproduced it anyway**,
in a smaller way, and it is worth recording exactly how.

I changed `push_delivery.rs`, ran `cargo clippy -p a2a-protocol-server
--all-targets --all-features`, got a clean result, and moved on. The full
preflight then failed two gates:

```
error: used underscore-prefixed binding
  --> .../push_delivery/mod.rs:101:22
error: this function has too many lines (74/60)
  --> .../push_delivery/tests.rs:215:7
```

The first only appears in a build **without** the `tracing` feature, because
that is the build where `_delivered`'s only other reader disappears and my new
use of it becomes the sole one. `--all-features` cannot see it. This is the
same mechanism as before — a feature-conditional lint — and knowing about the
mechanism did not stop me, because I still ran the one command that felt
sufficient rather than the one that copies CI.

The lesson is not "remember the matrix". It is **run `scripts/preflight.sh`
before you believe anything, including when the change looks local**. The script
exists, it reads its gate list from `ci.yml` so it cannot drift, and it costs
wall-clock rather than attention. I have used it for every subsequent change in
this branch.

Second, smaller, and also mine: `preflight --full` filled the disk (Q3), which
cost about an hour of re-running from a clean `target/`. That one is the tool's
to fix, and this branch fixes it (**B7**) — but the working-method half is:
**run the expensive check first, on a clean tree, before you have edits to
lose.**

### Process

**1. Close the `GITHUB_TOKEN` push loophole as a class, not as an instance.**
Q6 is the second gate found whose trigger does not cover the event that breaks
it (`dco.yml` was the first). Both were found by a human reading trigger blocks.
`scripts/prove_workflow_gates_fail.py` proves gates can *fail*; nothing proves
gates *run on the commits that can break them*. A checker that reads each
workflow's `on:` block, and each `git push` in the repository's own workflows,
and asserts that every gate-bearing job is reachable from every event that can
change its inputs, would have caught both. That is the highest-leverage new gate
I can name, and it is real work — a day, not an hour. **B13.**

**2. Prefer "make the numbers agree by construction" to "check that the numbers
agree".** The benchmark-prose gate was correct and unsatisfiable at the same
time, because two components computed the same quantity from different
precisions. The fix that stuck was making the generator quantise, not making the
checker lenient. Where this repository has a checker and a generator for the
same fact, the generator should consume exactly what the checker will read back.

**3. Say what a documented measurement's *method* is, in a script.**
CONTRIBUTING's "26 unwrap/expect" is now unreproducible by its own description
(Q6). Every other load-bearing number here — file lengths, book ignores,
benchmark prose, OTel coverage, method denominator — has a script. That one does
not, and it is the one that decayed. **B5.**

### Architecture

**4. Delete scaffolding for shapes the code does not have.** The
`Semaphore::new(16)` in `push_delivery` and the `#[allow(dead_code)]
write_timeout` were both future-proofing. Both read, to anyone auditing, as
protections that existed. One of them was covering a defect that took eight
seconds to demonstrate. A comment saying "we do not bound this, here is the
arithmetic that decides it" is worth more than a semaphore that bounds nothing.

**5. Publish primitives with their integration, or say loudly that you are
not.** `sign_agent_card`/`verify_agent_card` are good code with good tests, and
two crates advertise features named for them that wire up nothing. The
consequence is a user who turns on `signing` and believes their cards are being
verified.

### Priority

If I had to pick three things for the next release, in order:

1. **`AgentCard::new` reaching the prelude** (**B1**). It is written and tested;
   it needs the release that makes it reachable. Nothing else in the backlog
   changes what a new user meets in their first five minutes.
2. **The trigger-coverage gate** (**B13**). Two instances is a class.
3. **A troubleshooting chapter and an observability chapter** (**B10**). 45
   chapters and none of them is the page an operator opens at 3am — and this
   branch just added two new signals (`SKIPPED`, the queue-full error) that
   nothing tells anyone to look for.

What I would **not** prioritise: the SQLite artifact-normalisation schema change
from §3. It is the biggest performance win available and it is a schema
migration for a store with, on the evidence of Q"downloads", very few
deployments to migrate. Do it when there is someone to do it for.

# Addendum 7: what a second pass found, after "the branch is done and green"

Addendum 6 ended with a green CI run and a list of what was left. That was
premature, and the correction is worth more than the list: **asked to look
again, a second pass found five more defects in about the same time as the
first**, three of them the same shape as findings already in this document.

The rate of finding had not dropped. Stopping was a decision about effort, and
I presented it as a property of the tree.

## The class, now with five instances

Every one of these is: **a documented, public, configurable bound that a wider
bound silently preempts, or a claimed exclusion that does not exclude.**

| # | where | claimed | measured |
|---|---|---|---|
| 1 | `InMemoryQueueWriter::write_timeout` | 5s deadline on queue writes | never applied; blocked 1,024 events in, still blocked at 8s |
| 2 | `push_delivery_timeout` vs `HttpPushSender` | 3 attempts, 30s each, `[1s, 2s]` backoff | 1 attempt; outer bound fires at 5.001s |
| 3 | `shutdown_with_timeout(t)` | returns within `t` | returns within **2t** — measured 60s for `t = 30s` |
| 4 | `codecov.yml` `ignore:` | five PostgreSQL files excluded | none excluded; 881 of 2,096 missed lines |
| 5 | `mod warning` capture tests | assert what was logged | assert nothing, if another test reaches the callsite first |
| 6 | `tenant_resolver` module docs | "resource isolation" | three resolvers, all reading client-controlled input, no precondition stated where the resolver is chosen |
| 7 | `discovery::fetch_card_with_metadata` | a 30s card fetch | **55.0s** — two independent 30s budgets, headers and body |
| 8 | `auth::http_get_json` (JWKS + OIDC) | a 30s fetch | **unbounded** — the 30s covers headers only; the body loop has a size cap and no deadline. Still running at 45s. |

### 3 is the one that should not have survived

`shutdown_with_timeout` ran its drain phase to `now + timeout` and then handed
the executor's cleanup hook a *fresh* full `timeout`. MEASURED, paused time,
undrainable queue, hook that never returns:

```
PROBE: caller asked for 30s
PROBE: shutdown actually took 60s
PROBE: ratio = 2.00x
```

**The client already fixed exactly this bug, and wrote down why.**
`transport/jsonrpc.rs:225`:

> Single deadline across header fetch AND body read, so `request_timeout` is a
> true per-call budget rather than being applied twice (headers, then body) —
> which previously let a slow server hold the call for up to 2× the configured
> timeout.

Same defect, same 2×, same reasoning, one crate away — and it was never carried
across. A fix written down as a lesson is not the same as a lesson learned; the
only thing that generalises a fix is a check that looks everywhere.

The consequence is operational, not academic: the number an operator puts in
`shutdown_with_timeout` is the number they put in
`terminationGracePeriodSeconds`, and a process that overruns it is `SIGKILL`ed
part-way through the cleanup graceful shutdown exists to perform — truncating
exactly the streams it was protecting.

### 7 and 8 were found by following the class, not by reading more code

Both came out of one grep — the 24 non-test `tokio::time::timeout` sites this
branch enumerated — and both are the same defect the client crate had already
fixed and documented.

**Discovery.** `fetch_card_with_metadata` wrapped the request in one 30-second
timeout and the body read in another. MEASURED, against a socket that stalled
25 seconds before its status line and then dripped a chunk every 200ms:

```
PROBE: elapsed = 55.004750774s
PROBE: client error: transport error: agent card body read timed out
```

The error names the body read, which had been handed a fresh full budget after
the headers spent 25 seconds of the previous one. Discovery is the worst place
in the client to have this: it is the first thing done against an unknown peer,
nothing has authenticated the far end when it runs, and `resolve_agent_card`
and `fetch_card_from_url` are public functions that take no timeout at all.

**JWKS and OIDC discovery.** `http_get_json` bounded `client.request` at 30
seconds and then accumulated the body in a loop bounded by a *size cap and
nothing else*. A size cap bounds memory. MEASURED, against a server that
answered its headers at once and then wrote one byte every 300ms — far under
the cap, so the cap never fired:

```
PROBE: elapsed = 45.001304486s
PROBE: STILL RUNNING after 45s — the body read has no deadline
```

This one is on the **request path**: a `kid` that misses the cache forces a JWKS
refetch inside token validation, so a hung or hostile identity provider becomes
an availability problem. It does not need to send anything large or malformed.
It only has to be slow.

Two shapes, one class. Five of the eight are "the budget applied twice"; three
are "the budget applied to half the operation". `transport/jsonrpc.rs` describes
the first shape exactly, and it recurred twice more after being written down.

### 6 is a precondition documented in the wrong place

All three shipped `TenantResolver`s read client-controlled input — a header, a
bearer token, a path segment — and none authenticates it.
`grep -i 'spoof|untrusted|trust|attacker|forge'` over `tenant_resolver.rs`
returned nothing, in a module whose first paragraph promises "resource
isolation".

The model is not missing from the codebase. `RequestHandler::resolve_tenant`
states it precisely — the resolver is authoritative because it reads "**trusted**
request context", a client-supplied `params.tenant` that disagrees is rejected
as a cross-tenant attempt, and `require_resolved_tenant` closes the fall-through
to the shared `""` partition. A previous session clearly fixed a real
cross-tenant bug to get there.

It is in the wrong place. "Trusted" is a precondition on the deployment, stated
where the value is consumed rather than where the resolver is chosen — and
nobody picks a resolver by reading the handler. `BearerTokenTenantResolver::new()`
is the sharp end: it uses the **raw, unverified** bearer token as the tenant
identifier, which is the same as having no tenancy and worse, because it looks
like having some.

The comparison that settles how much weight this deserves is already in the
codebase: `RateLimitConfig::trusted_proxy_hops` applies exactly this discipline
to `X-Forwarded-For`. Tenancy needed it more — it decides whose data you read,
not whose quota you spend — and did not have it.

### 5 is a test that passes for the wrong reason

Adding one ordinary test made `hung_cleanup_is_warned_about` fail 3 runs of 3
while passing under `--test-threads=1`. `tracing` caches callsite interest
globally on first reach and rebuilds it when the *global* dispatcher changes —
not when `with_default` pushes a thread-local one. A callsite first evaluated by
a test with no subscriber is cached as "never interested".

The direction matters. That test failed loudly; its sibling
`clean_shutdown_warns_about_nothing` asserts an *absence*, so with the callsite
disabled it passes for the wrong reason — and would keep passing if the warning
moved to the wrong branch, which is the mutation the pair exists to catch.

## What the second pass checked and found clean

Negative results, so the next pass starts further along instead of re-walking
these. All MEASURED or OBSERVED on 2026-08-19.

* **The push sender's SSRF defence.** Thorough: private/loopback/link-local/CGNAT
  rejection, the IPv6 encodings that smuggle IPv4 (`::ffff:`, NAT64 `64:ff9b::`,
  deprecated `::a.b.c.d`), DNS resolution checked against *every* returned
  address, and the validated IP pinned for the outgoing connection with the

  have to present a valid certificate for the attacker's hostname.
  `hyper_util`'s legacy client does not follow redirects, so there is no 302
  bypass either.
* **The JWT validator.** `alg: none` rejected with a hand-crafted-token test,

* **The client's retry/timeout composition.** No preemption: each attempt gets
  its own `request_timeout` and nothing wraps the retry loop. `request_timeout`
  is documented as "per-request", which is what it is.
* **The SSE client's idle behaviour.** `first_event_timeout` bounds
  establishment only and is lifted after the first chunk — stated plainly in the
  field docs and the setter, with the reason (long-idle subscriptions must not be
  cut off). A deliberate boundary, not an oversight.
* **A `#[allow(dead_code)]` sweep of library code.** Three hits, none of them a
  second `write_timeout`: two consts/functions used only under a feature, and
  `routing.rs`'s `Route::streaming`, whose comment says "used in tests" and which
  is used in tests. Worth noting *why* that one is fine and `write_timeout` was
  not: both carried the same annotation, and the difference is entirely in the
  comment beside it. "Used in tests" answers the reader's question. "Retained for
  API compatibility" answered it wrongly.
* **A scan for fields written but never read.** Two candidates, both false
  positives from a regex that could not see `self` and the field name on

## What this says about the method

Three process conclusions, none of them comfortable.

**A fix is not a lesson until something checks for the next instance.** The
client's 2× fix, the `codecov.yml` 2026-08-06 fix, and CONTRIBUTING's
`unwrap` count were all written down carefully and none of them generalised.
The things in this repository that *have* held — the file-length ratchet, the
gate prover, the method denominator, the OTel coverage check — are the ones
with a script behind them. **B14** below is that script for the timeout class.

**"Verified" needs a date, a command, and a re-run.** Two of these five are
claims that were true when written and stopped being true, in a repository that
is unusually careful about exactly that.

**Reading a rollup is not reading the data.** I did it in Q5, and it is why the
codecov finding took a second pass to surface.

## Class two: cleanup that cancellation skips

**State claimed on one code path and released on another, where dropping the
future runs neither.** In Rust the release has to be in `Drop`, or it is not a
release — it is a release *on the paths somebody thought of*. Continuing the
numbering from Addendum 7:

| # | where | claimed | measured |
|---|---|---|---|
| 9 | `InMemoryTaskStore` eviction slot | a sweep in progress is skipped, then re-enabled | one cancelled sweep disabled **all** eviction for the life of the process |
| 10 | WebSocket client, unary `pending` entry | removed on response, timeout, or teardown | 5 cancelled requests → **5** retained entries, indefinitely |
| 11 | WebSocket client, streaming `pending` entry | removed on terminal event, sentinel, or closed consumer | 5 abandoned streams → **5** retained entries, indefinitely |

### 9 — one cancelled sweep, and the store never evicts again

`maybe_evict` used a compare-and-swap on an `AtomicBool` to make sure two
sweeps never run at once, and stored `false` back at the end of the function.
Between those two lines it takes the store's write lock, which is an `.await`.
A future dropped while parked on that lock never reaches the store.

MEASURED — the probe claimed the slot, parked on a held write lock, and was
then dropped:

```
PROBE: slot claimed while parked on the lock = true
PROBE: slot still claimed after cancellation = true
PROBE: slot after a later maybe_evict     = true
```

The third line is the damage. Every later call returns immediately, forever.
**Both** of the in-memory store's memory bounds — TTL expiry and capacity
eviction — run through that slot, so the store that this document elsewhere
describes as "has a capacity bound and amortised eviction" (§ Q7) had neither,
from the first cancellation onward. `InMemoryTaskStore` is the default store,
and the default is what an evaluation runs.

Fixed with an RAII guard, so the release is the `Drop` of the claim:

```rust
struct EvictionSlot<'a>(&'a AtomicBool);

impl<'a> EvictionSlot<'a> {
    fn claim(flag: &'a AtomicBool) -> Option<Self> {
        flag.compare_exchange(false, true, Ordering::AcqRel, Ordering::Relaxed)
            .is_ok()
            .then_some(Self(flag))
    }
}

impl Drop for EvictionSlot<'_> {
    fn drop(&mut self) { self.0.store(false, Ordering::Release); }
}
```

Repro: `cargo test -p a2a-protocol-server --lib
a_cancelled_sweep_releases_the_eviction_slot`. Proven able to fail two ways —
with the original CAS/store pair restored, and with the guard claimed and then
`mem::forget`ed.

### 10 and 11 — the WebSocket client's pending map

`WebSocketTransport` multiplexes requests over one connection and routes
responses through `HashMap<String, PendingRequest>`. The map has **no capacity
bound** and lives as long as the connection, which is meant to be long-lived.

Entries were removed on three paths: a response routed to them, the explicit
timeout branch in `execute_request`, and `fail_all_pending` at teardown. A
caller whose future is dropped takes none of the three.

MEASURED, against a server that completes the handshake and then answers
nothing — five requests each abandoned after 80ms against a 30-second
transport timeout:

```
PROBE: pending entries after 5 cancelled requests = 5
```

Following the class rather than stopping at the instance found the same thing
at the other end. A streaming entry is removed by `route_frame` on a terminal
event, on the end-of-stream sentinel, or when a send finds the consumer gone —
**all three require a frame to arrive**. A server that accepts a subscription
and says nothing sends none, the consumer times out on `first_event_timeout`
and drops the stream, and nothing runs:

```
PROBE: pending entries after 5 abandoned streams = 5
```

Both are 0 after the fix. Repro:

```
cargo test -p a2a-protocol-client --features websocket --lib pending_entry
```

#### Why the obvious fix would not have worked

A `Drop` guard on the caller's side is not sufficient on its own, because the
*writer task* did the registering:

```rust
while let Some(cmd) = write_rx.recv().await {
    let mut map = pending_for_writer.lock().await;   // insert here…
    map.insert(cmd.request_id, cmd.pending);
```

A caller cancelled between `write_tx.send(...).await` and the writer's insert
would drop its guard first, remove nothing, and the writer would then insert an
entry with no owner — a narrower race, still unbounded. Registration therefore
moved to the caller, and `WriteCommand` lost two of its three fields. The
ordering the writer needed (entry exists before the frame is sent) is preserved
a fortiori: the caller inserts before it queues the command.

The streaming entry has to outlive `send_streaming_request`, so its guard
travels with the returned `EventStream` — which already owns an `AbortHandle`
for exactly this reason. Three tests, and the third exists because without it
the first two pass for the wrong reason: removing the entry unconditionally
satisfies both leak tests and breaks every live stream.

#### One thing the fix depends on, checked by the compiler rather than by me

Removing an entry from `Drop` means the lock cannot be a Tokio mutex. I audited
all eight `.lock().await` sites by hand — seven in the transport, one in its
tests — and concluded none holds the guard across an `.await`. That audit is worth exactly nothing on its own — but a
`std::sync::MutexGuard` is `!Send`, so a future that holds one across an
`.await` fails to compile against the transport's `+ Send` bound. Switching the
mutex converted my reading into a compile-time check. Where a property can be
made the compiler's problem, my having read the code carefully is not evidence.

#### What clippy caught that `cargo build` did not

Both defects were fixed and the full client suite was green under
`cargo build`/`cargo test` before `cargo clippy --all-targets` across four
feature configurations found two more problems: `fail_all_pending` was still
`async` with nothing left to await, and `EventStream::holding` was gated
`any(test, feature = "websocket")` and so compiled-but-unused in a
`--no-default-features --all-targets` build. A third — `EventStream`'s new
field being `dead_code` in every build where `holding` is gated out — only
appeared while *proving a test could fail*, and is now handled by taking the
field explicitly in `Drop` rather than leaving it to drop glue.

That is three separate warnings from configurations a green `cargo test` never
compiled, on a change whose diff is 300 lines in two files. It is the same
lesson as Addendum 6's `used_underscore_binding` finding, and I had to learn it
twice in one branch.

## Class three: a bound that covers half of what it names

Auditing the *server* half of the WebSocket binding turned up a different
shape again — not a bound applied twice, and not cleanup that cancellation
skips, but **a bound that covers the first half of a connection's life and
nothing after it.**

`dispatch/websocket.rs` documents its handshake timeout in exactly those terms:

> Without this bound, a client that opens a TCP connection and never sends the
> HTTP upgrade request pins a file descriptor and a task for the life of the
> process (slowloris) — `accept_async` has no timeout of its own.

The author of that comment was thinking about precisely this attack. And then
`read_loop` awaited `reader.next()` with no bound at all, and `accept_loop`
spawned a task per accepted socket with no ceiling. MEASURED, 2026-08-19:

```
PROBE: idle handshaken connections held = 400
PROBE: oldest connection after 12s idle -> served normally
```

400 is where the probe stopped, not where the server refused; nothing was
refused. The ceiling is the process's file-descriptor table.

This is a real asymmetry with the HTTP path, not a matter of taste. `ServeConfig`
bounds all four of these and states its own policy plainly: *"The two timeouts
default to on, which is a deliberate difference from `max_connections`: a
deployment might genuinely want no connection ceiling, but nobody wants a
slowloris to be free."* A post-handshake idle WebSocket was a free slowloris,
by that document's own standard, on the same server.

### The interesting part is why the idle timeout could not simply be copied

On HTTP, silence means nothing is happening. On a WebSocket it may mean a
subscription is waiting for its next event, which is a legitimate thing to do
for hours. Porting `ServeConfig`'s default-on idle timeout would close healthy
subscriptions — the exact failure `ServeConfig`'s own doc warns about for SSE,
one binding over.

So `with_idle_timeout` is **opt-in**, and what makes it *worth* opting into is
that it distinguishes quiet from dead: at the halfway mark the server sends a
WebSocket Ping, conformant client libraries answer automatically, and that Pong
is traffic. Outbound frames count too, via a per-connection activity clock the
write path touches, so a stream pushing events to a silent consumer keeps its
own connection alive. `with_max_connections` takes its permit **before**
`accept()`, so excess load waits in the kernel's listen backlog rather than as
unbounded spawned tasks — the same design as `ServeConfig`.

Repro: `cargo test -p a2a-protocol-server --features websocket --lib
dispatch::websocket`. Four tests, each proven able to fail.

### Two things I got wrong while doing it, both worth recording

**My first probe reported the opposite of the truth.** It asked whether the
oldest connection was "still served" with `matches!(got, Ok(Some(Ok(_))))` — and
a *Close* frame matches `Ok(_)`. It reported a closed connection as healthy. The
same class as finding 5 in Addendum 7, committed by me, an hour after writing
that section up. A probe needs its negative case checked as carefully as the
code does.

**My first idle test modelled the wrong peer.** It drained the client's stream
while the budget ran, so tungstenite answered the keepalive automatically and
the connection stayed up — correct behaviour, failing test. The fix was to stop
polling: a peer that has stopped reading its socket is the only peer this bound
is entitled to close. The test that would have hidden this is the one that
*passes* — and there is one, `the_defaults_are_no_idle_timeout_and_no_connection_ceiling`,
whose first version idled for three seconds and passed unchanged against an
injected 75-second default. It now asserts the fields directly, because any
duration a behavioural test picks is shorter than some default it would fail to
notice.

## The store's concurrency, audited beyond the eviction slot

The eviction slot (item 9) was the defect. The rest of the audit found the
store's concurrency **sound**, and one more documented property that the code
does not have.

### What checked out

MEASURED, not read:

| property | measurement |
|---|---|
| capacity bound under concurrency | 16 writers × 200 saves against `max_capacity(100)` → final count **exactly 100**, for terminal *and* non-terminal tasks |
| transient overshoot | a concurrent reader sampling throughout saw a peak of **102** — bounded by writes in flight, self-correcting on the next write |
| `save` returns within the bound | asserted with no intervening sleep or yield, so a spawned sweep would not have run |

The index design holds up on reading too: one `RwLock` over the primary map and
both secondary indexes, so they cannot disagree; `next_seq` is a `u64` under
that same lock, so the pagination cursor is collision-free by construction;
`insert_if_absent` does its check and its insert in one lock acquisition rather
than two.

### What did not: "runs as a background task"

`InMemoryTaskStore`'s own type documentation said:

> Eviction runs as a **background task** every N writes … The eviction sweep is
> decoupled from the `save()` write lock so that **writers are not blocked**
> during the O(n) cleanup.

There is no `spawn`. `maybe_evict` is awaited inside `save`, and it holds the
write lock for the whole sweep. What is decoupled is the *lock acquisition* —
the insert's lock is released before the sweep takes its own — which is a much
weaker property than either sentence claims.

MEASURED, 50,000 terminal tasks, `eviction_interval` 1000, timing 1,000
consecutive saves so exactly one lands on the interval:

```
PROBE: 50k entries — quietest of 1000 saves = 3.986µs
PROBE: 50k entries — slowest of 1000 saves = 4.541389ms
PROBE: ratio = 1139x
```

The capacity pass is not the problem — 3.5–3.7× across two runs at 10,000
entries, because it removes the overflow rather than scanning for it. The TTL pass is O(n) and
unavoidably so, which is precisely why it is amortized behind
`eviction_interval`.

**Classification: documentation gap, not a defect.** The behaviour is
reasonable and the alternative is worse (a spawned sweep still takes the write
lock; it just moves the stall to a writer that did not earn it). What was wrong
is that the paragraph an operator reads to size a latency budget described a
design this store does not have, and it named the two properties — background,
non-blocking — that would have made the number not matter. Corrected in place
with the measurements, plus a note that `eviction_interval` is a tail-latency
knob and that a p99.9-sensitive deployment should raise it and drive
`run_eviction()` from its own scheduler.

A test now pins the observable half (`save` does not return over capacity),
because that is the part a future refactor could silently change. A stale
comment calling a synchronous `.await` "the maybe_evict background task", along
with the 10 ms sleep that comment justified, is gone with it — the sleep was
waiting for something that had already happened.

### The same gap, same numbers, in the gRPC dispatcher

Recorded first as OBSERVED-not-measured, because it had been read and not run.
`GrpcDispatcher::build_router` sets `concurrency_limit_per_connection` and the
two message-size caps and nothing else. MEASURED the same day:

```
PROBE: idle TCP connections held = 400
PROBE: oldest idle connection still writable after 12s = true
```

Identical to the WebSocket numbers. Fixed with `with_http2_keepalive` and
`with_max_connection_age`, both opt-in, both passing through to tonic — HTTP/2
keepalive being the gRPC-native form of the same ping-to-tell-quiet-from-dead
argument.

Two things are named rather than implied. There is still no connection
*ceiling*: tonic has no `max_connections`, and adding one means yielding an IO
wrapper that owns a semaphore permit through tonic's `Connected` trait, which
is a real change rather than a passthrough. And the test for the knobs asserts
the fields, not the passthrough — deleting the two `http2_keepalive_*` calls
leaves it green, verified by mutation, because tonic exposes no way to read a
`Router`'s keepalive back. Both are written into the code, not just here.

## Class three again, in the binding nobody had measured: multicast fan-out

The WebSocket finding was "a bound that covers the first half of a lifecycle".
This is its sibling: **an isolation mechanism that covers one of the two things
its own comment claims.**

`SlimRpcMulticast::stream_message` gives every invited agent its own bounded
channel, under this comment:

> One channel per invited agent, so a slow or silent agent cannot hold up
> another's events.

The split does exactly that for a **silent** agent, which produces no frames at
all. It does nothing for a **slow consumer**, because every member's frames
arrive through one shared loop, and that loop awaited `send` on the member
channel. A consumer that stops reading fills its 64-deep channel, the shared
loop parks, and every other member's stream stops.

MEASURED, two agents each emitting 300 events, one consumer never polled:

```
PROBE: live member saw 151/300 events in 25.001717413s; completed = Err(Elapsed(()))
```

The live member's stream stopped at 151 events and never resumed. With the
non-blocking send:

```
PROBE: live member saw 300/300 events in 220.162285ms; completed = Ok(true)
```

### Why dropping is the right answer here, and what makes it safe

One source, N consumers with independent rates, bounded memory: something has
to give. Blocking is what it did. Unbounded buffering reintroduces the OOM this
repository bounds everywhere else. So: drop, and *tell the consumer*. That is
the contract the SSE fan-out already has through broadcast's `Lagged`, and this
binding now matches it — a member that falls behind receives an error naming
how many events it missed, before the next event it does receive.

A task event stream is ordered state. A consumer silently skipped from
`Working` to `Completed` cannot tell that from a task that did exactly that,
which is why the report is not optional.

### The bug in my own fix, caught by its own test

The first version reported a gap only on the send that carried the *next*
event. A member that falls behind on the last events has no next event, so its
report was never delivered and its stream just ended — indistinguishable from a
clean end. `a_consumer_that_falls_behind_is_told_what_it_missed` failed on
exactly that, which is what the test was for. The fan-out now flushes pending
reports when the source is exhausted, bounded by `LAG_REPORT_FLUSH` so a
consumer that never reads cannot hold the task open.

Three tests, each proven able to fail: with the awaiting `send` restored (two
fail), with every send counted as dropped (three fail, including the control),
and with the tail flush removed (one fails). The control —
`every_member_gets_every_event_when_its_consumer_keeps_up` — exists because
without it the other two pass for a binding that drops everything.

### What this says about the audit itself

Addendum 7 listed SLIMRPC backpressure as "neither specified nor implemented"
and called it *"the first thing I would look at next"*. It then went unexamined
for two more passes, because it was on a list rather than in a diff. It took
one probe to find, and the probe took twenty minutes.

## The same shape once more: a memory bound that buys an availability problem

`TenantStoreConfig::max_tenants` (default 1,000) was documented as:

> Prevents unbounded memory growth from tenant enumeration attacks.

True, and one step short of the consequence. Tenant ids come from `RequestHandler::resolve_tenant`, and **every bundled
resolver reads client-controlled input** — the same fact Addendum 7 item 6 established about the resolver module
and which is now written where the resolver is chosen. So an enumerator does
not get memory. It gets a lockout: once the table is full, *every new tenant is
refused*, legitimate ones included.

The reclamation path, `prune_empty_tenants`, is not automatic — nothing calls
it — and only removes partitions whose task count is **zero**. A partition
created by a `save` holds a task until it is evicted, so at the shipped
one-hour TTL a burst of 1,000 junk tenant ids locks out new tenants for an hour
*even with pruning scheduled*.

MEASURED (`a_full_tenant_table_refuses_new_tenants_and_pruning_does_not_help`,
`max_tenants: 2`): two junk tenants fill the table, a legitimate third is
refused, `prune_empty_tenants()` reclaims nothing, the legitimate tenant is
still refused; delete the junk tasks, prune again, and it gets in.

**Classification: documentation gap, not a defect.** The cap is doing its job
and removing it would be worse. What was missing is that the sentence an
operator reads when sizing it named only the half that is comfortable. Both
`max_tenants` and `prune_empty_tenants` now say what they do, including that
the mitigation is scheduled by the operator or not at all, and that raising the
cap is only safe alongside the authenticated-tenant-id precondition the
resolvers state.

## Class four: a panic where nobody can see it

`panic = "abort"` in this workspace's release profile (`Cargo.toml:88`) changes
what a panic *is*. In a debug build a panicking spawned task is a lost task; in
release it is a lost process. Two places had not been read with that in mind.

### `spawn_signal_watcher` could abort the process minutes after startup

`HotReloadAgentCardHandler::spawn_signal_watcher` returned a `JoinHandle` and
registered its SIGHUP handler **inside** the spawned task:

```rust
let mut stream = signal(SignalKind::hangup()).expect("failed to register SIGHUP handler");
```

The function's own docs carried a `# Panics` section for it — attached to a
function that cannot panic, describing a panic that happens somewhere else,
later, in a detached task the caller cannot join in time and cannot catch at
all under `panic = "abort"`.

**I got the fix wrong on the first attempt, and only a probe caught it.** I
assumed `signal()` returns `Err` on a runtime with no signal driver and wrote a
`match` that logs and exits. MEASURED:

```
PROBE: signal() PANICKED: there is no signal driver running, must be called
from the context of Tokio runtime
```

It panics. My `match` handled a case that mostly does not arise and left the
one that does. That is the standing order — never assume — failing in the
middle of a session whose whole subject is claims that were never checked, and
the only reason it did not ship is that I probed a behaviour I was sure of.

The reachable failure is ordinary, not exotic: any caller who builds their own
runtime with `Builder::new_current_thread().enable_time()` rather than
`enable_all()`. Since `catch_unwind` cannot help under `abort`, the fix is to
move the panic to where it is *useful*: registration is now synchronous inside
`spawn_signal_watcher`, so it fires in the caller's startup path, deterministic
and immediate — a failing first test run instead of an abort at 3am — and the
`# Panics` section now describes the function it is attached to. The genuine
`Err` path (an `io` failure from `sigaction`) still logs and exits without
taking anything down.

The same loop also discarded the `Option` from `stream.recv().await`. `None`
means no further signals can arrive, and the loop answered that by asking again
immediately, forever. A latent hot loop, now a `while … .is_some()`.

### The agent-card handler turned one panic into permanent failure

`current()` and `update()` both `expect`ed on their `std::sync::RwLock`.
Poisoning is sticky, so *one* panic under the write lock made `current()` — the
function that answers `GetAgentCard` — panic on every subsequent call. Under
`panic = "abort"` the second panic ends the process.

Both now recover, and recovery is correct rather than convenient: the only
write is a whole-value assignment of an already-constructed `AgentCard`, so
there is no state in which a reader could see a half-updated one. It is the
same reasoning the rest of the workspace already applies to its `std` mutexes —
this file simply predated it.

Repro: `cargo test -p a2a-protocol-server --lib hot_reload`. Two tests, each
proven able to fail: with the `expect` restored on `current()`, and with
registration moved back inside the spawned task.

### And the same shape, committed by me, in this branch

Three doc comments on the event queue said the persistence channel "will never
lose events", "will never lag", and that the processor "must never miss
events". All three are false, and two of them sit within twenty lines of the
`write_timeout` fix I made *earlier in this same branch* — the fix whose entire
subject is that a full persistence channel is a real state with a real
consequence.

There are two ways not to deliver, and they call for opposite responses: full
past the deadline returns an error naming the stalled processor, and **closed
drops the event and returns `Ok`**, reported only by a `trace_warn!` that
compiles to nothing without the non-default `tracing` feature. The second is
deliberate and defensible; being invisible on a default build is not, and is
now backlog **B18**.

I changed the behaviour and left the neighbouring sentences describing the old
one. That is the same failure this document has spent two addenda cataloguing
in other people's commits, and it took a mechanical sweep for words like
"never" and "guarantee" to find — not re-reading my own diff, which I had done.

### Why a `# Panics` section is not evidence

Both defects were **documented**. The `# Panics` sections were there, accurate
in the narrow sense that a panic can occur, and useless: one named the wrong
function, the other named a condition (`RwLock` poisoned) without saying that
meeting it once disables the API forever. A doc comment that records a hazard
is not the same as a design that survives it, and this repository's own
`unwrap_or_else(PoisonError::into_inner)` idiom — used correctly elsewhere in
the same crate — is the evidence that somebody already knew the better answer.

## New backlog

### ~~B19~~ — measured and closed: the gRPC dispatcher had the same gap
* **Recorded as OBSERVED and not measured**, deliberately, because it was read
  rather than run. Measured the same day, and it reproduced exactly:

  ```
  PROBE: idle TCP connections held = 400

* **Not shipped, and worth naming:** a connection *ceiling*. tonic has no

  one-line passthroughs would have hidden it.
* **Also still true:** `GrpcConfig` is a plain `pub struct` with public fields
  and no `#[non_exhaustive]`, which is why these knobs live on the dispatcher
  rather than the config. Marking it `#[non_exhaustive]` is itself a breaking
  change, so it belongs in a deliberate minor rather than here.

### B18 — A metric for the silently-dropped persistence event
* **Evidence:** `InMemoryQueueWriter::write` drops the event and returns `Ok`
  when the persistence channel is **closed**. That is the right behaviour — the
  processor is gone, the stream can still serve live subscribers — but the only
  report is a `trace_warn!`, which compiles to nothing without the non-default
  `tracing` feature. On a default build the loss is silent, and it is exactly
  the loss an operator would want to see, because the task's stored state stops
  advancing while its stream keeps delivering.
* **Fix:** a counter, as `push_outcome::SKIPPED` is for the push path. The
  writer holds no metrics handle today, so this is a plumbing change, not a
  one-liner — which is why it is a backlog item and not part of the doc
  correction that found it.
* **Cost:** half a day. **Done when:** a closed persistence channel moves a
  counter on a build with no non-default features.

### ~~B16~~ — done: `scripts/check_cancellation_release.py`
* **Evidence:** three instances above, in two crates, none found by the first
  pass.
* **What shipped, and what it deliberately does not do.** The spec here
  proposed "a lint pass over `compare_exchange`/`store`, `insert`/`remove`, and
  `fetch_add`/`fetch_sub` pairs in the same function". That is too wide to
  survive contact: an `insert`/`remove` heuristic fires on every cache in the
  workspace, and a check people learn to override is not a check — the argument
  `check_file_lengths.sh` already makes for its own ratchet. What shipped is the
  narrow half with exactly one correct form: a file that **claims** a guard slot
  with `compare_exchange(false, true, ..)` must contain an `impl Drop` that
  **releases** one with `store(false, ..)`.
* **Its acceptance criterion, met.** The spec said "done when it fails if
  `EvictionSlot`'s `Drop` is replaced by a store at the end of `maybe_evict`."
  Verified by doing exactly that: the check exits 1 and names
  `eviction/mod.rs:89`. Registered in `prove_gates_fail.sh` with its own
  injection, as every gate here must be.
* **Two things the first version got wrong**, both worth recording because both
  are the failure this document is about:
  * It matched the claim's field name against the release's, and so flagged the
    *correct* code — a guard holds a borrowed reference, so `EvictionSlot`
    claims through `flag` and releases through `self.0`. A check that fails on
    the canonical fix is worse than no check. The invariant is now the weaker,
    true one: this shape and its release live in the same file.
  * It truncated each file at the first `#[cfg(test)]`, which in
    `eviction/mod.rs` is `#[cfg(test)] mod fixtures;` on line 29 — a *file*
    declaration, not an inline module. So it read the first 29 lines of the one
    file it exists for, found nothing, and printed a confident zero. It now
    blanks only inline `#[cfg(test)] mod … { … }` bodies, by brace matching,
    and preserves offsets so reported line numbers stay true.
* **Cost:** the estimate said a day and a half for the wide version. The narrow
  one took about an hour, and is the one that can stay switched on.

### B17 — Bound the WebSocket client's pending map
* **Evidence:** the map is `HashMap<String, PendingRequest>` with no capacity
  limit. The two leaks above are fixed, so nothing *known* grows it without
  bound — but "no known leak" is what was true yesterday.
* **Fix:** a cap, and a `ClientError` when a request would exceed it. The server
  side already does this for its own concurrency (`Semaphore::new(64)` with a
  real `try_acquire` and a `-32000 "server busy"` response); the client has no
  equivalent.
* **Cost:** half a day. **Done when:** the N+1st concurrent request on one
  connection is refused rather than queued invisibly.

## Where to pick up, revised

Four passes have now each found defects the previous one was not looking for,
at roughly a constant rate. That is the fact the ordering has to answer to.

1. **B14, B16, B13 — the three detectors, first and together.** Thirteen of the
   twenty findings in Addenda 7 and 8 (eight and twelve respectively) fall
   into two mechanical shapes — a bound preempted by a wider one, and state
   released off the cancellation path — and every single one was found by a
   person reading code on purpose. Three of
   them had already been fixed *and written up* elsewhere in this same
   workspace, which is the strongest possible evidence that prose does not
   generalise a fix and a script does. Doing these first is not tidiness — it
   is the only item on this list that changes the rate of the others.
2. **B19 — measure the gRPC dispatcher.** It is the one place I named a defect
   without measuring it, and it should not stay that way.
3. **B12 — coverage for the SLIMRPC binding**, then B11's example. The binding
   is unpublished and, apart from the multicast fan-out measured here, still
   unmeasured. That fan-out was carrying the same class as the WebSocket
   findings and had been sitting on a backlog list, named as the next thing to
   look at, for two passes.
4. **B1 — release, then reach the constructors from the prelude.**
5. **B17, B18, B3, B15** — bounded, each closes a measured hole.
6. **B10 — the four chapters**, B2, B4, B5, B6, B9.

### What I would tell the next pass

Not "the tree is clean now". Four passes, four sets of classes, no sign of the
rate dropping. What has changed is that the *shapes* are written down: read
this document's class tables first and grep for them, rather than reading files
in order and hoping. And when a fix is landed, ask the question that would have
saved three of these — *where else is this true?* — before the commit, not two
addenda later.
