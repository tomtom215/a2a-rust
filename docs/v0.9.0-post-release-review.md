# Post-v0.9.0 review

A critical read of this repository after the 0.9.0 release, written against
first-hand measurement rather than against the repository's own claims about
itself. Every number below was produced on this checkout during the review;
where something was *not* verified, it says so.

Two things frame it. The `a2a-protocol-types` crate has passed 20,000 downloads
(25,022 total / 24,268 in the last 90 days, crates.io API, 2026-08-17), so
mistakes here reach people. And since this project started, the A2A project has
published **its own Rust SDK** — `a2aproject/a2a-rs` — which changes what
"complete" has to mean.

## What was verified, and what it showed

| Check | Command | Result |
|---|---|---|
| Workspace build | `cargo build --workspace --all-features` | exit 0 |
| Workspace tests | `cargo test --workspace --all-features` | exit 0 — **2,837 passed, 0 failed, 157 ignored** |
| SLIMRPC binding build | `cargo build --all-targets` in `bindings/` | exit 0 |
| Vendored SLIMRPC spec vs upstream | `scripts/check_slimrpc_spec.sh` | exit 0 — 2 files match |
| Vendored protos | `scripts/check_proto_copies.sh` | exit 0 — 5 files × 4 copies identical |
| File-length ratchet | `scripts/check_file_lengths.sh` | 80 of 409 over 500 lines, all recorded |
| Book `ignore` ratchet | `scripts/check_book_code.sh` | 130 blocks across 21 files, matches baseline |
| API reference names | `scripts/check_api_reference.py` | 116 names, all defined |

The suite is real and it is green. The README said "~2,740 tests"; the measured
figure is 2,837 passing. Stale, and in the conservative direction — corrected in
this branch.

**Panic discipline is genuinely good, and is worth stating because it is the
thing most often wrong in a Rust server SDK.** Excluding `#[cfg(test)]` modules,
`build.rs`, benches, and doc comments, there are **52** `unwrap`/`expect`/`panic!`
sites across all four crates, and the runtime ones are lock-poisoning `expect`s
plus one `signal(SIGHUP)` registration. There are **zero** `TODO`/`FIXME`/`HACK`
markers in `crates/*/src` or `bindings/*/src`. This is not a weak area.

---

## 1. The thing that changed: there is now an official Rust SDK

`a2aproject/a2a-rs` publishes six crates. `a2a-lf` has **31,655** downloads
against this project's `a2a-protocol-types` at **25,022**. It is not a
side project — it is the A2A project's own.

| | this project | `a2aproject/a2a-rs` |
|---|---|---|
| Bindings | JSON-RPC, REST, **WebSocket**, gRPC, SLIMRPC | JSON-RPC, REST, gRPC, SLIMRPC |
| Server base | raw `hyper` 1.x, Axum optional | `axum` |
| MSRV | **1.93** | **1.85** |
| CLI | — | `a2acli` |
| Card-driven transport selection | four built-in bindings only | `TransportFactory`, SLIMRPC included |
| Conformance evidence | official TCK 92/114 MUST, in-repo runner, ITK, mutation ledger | none published |
| SLIMRPC multicast (`slimrpc-multicast.md`) | **implemented** | not implemented |
| SLIMRPC `Collaborate` (collaborative channel) | **not implemented** | implemented |

Read honestly, this project is ahead on transports, on testing, and on evidence,
and behind on three things that decide adoption:

* **MSRV 1.93 vs 1.85.** Eight minor versions of Rust. This is the single
  largest adoption barrier in the repository, and it is now measurable against a
  direct alternative rather than against a hypothetical conservative user. The
  ROADMAP lists it as an open question; the answer got easier.
* **No CLI.** `a2acli` inspects cards and manages tasks. Evaluating this SDK
  requires writing Rust; evaluating theirs does not.
* **No card-driven transport selection for SLIMRPC.** Theirs resolves a card and
  dials whatever it advertises. Ours requires `with_custom_transport` by hand,
  because `builder/transport_factory.rs` knows four binding constants and has no
  registration hook.

None of these is a defect. All three are the reasons someone picks the other one.

## 2. SLIMRPC: what "complete" actually requires

The binding implements all eleven methods plus multicast, tested across ten
topologies with **37 integration test functions** and real SPIRE. The official
crate's suite is **4 test functions in one topology**. On depth this is not
close.

Reading `spec/slimrpc_v1/slimrpc.md` clause by clause against the
implementation, and against the official crate for comparison:

### 2.1 Service parameters are not transmitted (§3, a MUST)

§3: *"A2A service parameters … **MUST** be transmitted using the SLIMRPC
metadata mechanism"*, with `a2a-version: 1.0` as its own example.

`SlimRpcTransport`'s `metadata_from` forwards `extra_headers` and nothing else,
and `ClientRequest::new()` starts that map empty. Every other client transport
in this workspace injects the version explicitly —
`transport/jsonrpc.rs:199`, `rest/request.rs:101`, `websocket.rs:255`,
`grpc.rs:235`. **SLIMRPC does not.**

The server half matches: `headers_from(ctx)` returns `ctx.metadata()` raw, and
nothing validates a version. Every other binding does — `validate_version_header`
for JSON-RPC and REST, `check_a2a_version` for WebSocket, `validated_metadata`
for gRPC.

Two things make this more than a missing line:

* **An out-of-workspace binding cannot fix the server half.**
  `validate_version_header` is `pub(crate)` and `validated_metadata` is
  `pub(super)`. This is the same shape of problem as the missing
  `EventStream::from_event_channel` that building this binding already
  uncovered: the extension point is incomplete, and reading the signatures does
  not show it.
* **The official crate does not send it either** — checked against
  `a2a-slimrpc` 0.2.4's source. So this is not an interop break between the two
  implementations. It is a §3 MUST that neither satisfies, and the honest
  framing is "unimplemented by both", not "we are behind".

### 2.2 Internal SLIMRPC metadata leaks into the A2A header map

The official crate filters SLIMRPC's own keys — `deadline`, `status-code`,
`rpc-id`, `service`, `method` — before handing metadata to the handler
(`common.rs::is_internal_metadata_key`). Ours does not: `headers_from` returns
`ctx.metadata()` unfiltered, and that map is what feeds `RequestHandler`'s auth
and tenant resolvers. A `HeaderTenantResolver` keyed on a colliding name would
read transport plumbing as an A2A header. Narrow, but it is a correctness gap
with a known-good reference fix.

### 2.3 Address parsing is stricter than the spec's own examples

`SlimName::parse` requires the `slim://` prefix and rejects anything else. But
§2.1 of the same spec presents bare `mydomain/demo/echo_agent` as *the* SLIM
Name form, and the official crate accepts all three of `org/ns/app`,
`slim://org/ns/app`, and `slimrpc://org/ns/app`. A card written by the official
SDK using the bare form is rejected by ours. One `strip_prefix` chain fixes it.

### 2.4 Two spec observations worth recording

* The vendored spec's §1 says the service is `a2a.v1.A2AService`; both
  implementations use `lf.a2a.v1.A2AService`, which is what the ratified
  `a2a.proto` package actually is. The spec text is internally inconsistent with
  its own §4. **Both implementations agree, so there is no interop break** — but
  the repository vendors that spec and says nothing about the discrepancy.
* `scripts/check_slimrpc_spec.sh` compares two named files. It cannot see a
  *new* file appearing upstream. The official crate references a "collaborative
  channel extension spec" that is not in `a2aproject/experimental-cpb-slimrpc`
  at all — so the mechanism by which that binding grows is one this repository's
  drift check is structurally unable to notice.

### 2.5 The binding is outside every supply-chain gate

`bindings/a2a-protocol-slimrpc` is `publish = true`, ships 379 transitive
dependencies including a native C crypto build, and:

* `cargo deny` runs at the workspace root, so **none of those 379 are audited**;
* the `package` job's `cargo package --workspace` cannot see it, so **nothing
  validates that it packages or publishes**;
* it is in no coverage or mutation run.

Its CI job runs fmt, clippy, build, test, and SPIRE. That is good, and it is not
the same as the four workspace crates' gates. For a crate that is published to
users, the audit gap is the one that matters.

## 3. Worst performance: persisted streaming events

Measured on this checkout with a probe written for the review
(`SqliteTaskStore`, fresh database per arm, three interleaved repetitions,
best-of-3 per bucket, release build):

| artifact parts | `save_artifact_delta` | full `save` | ratio |
|---:|---:|---:|---:|
| 100 | 170 µs | 203 µs | 0.84× |
| 300 | 287 µs | 295 µs | 0.97× |
| 500 | 359 µs | 426 µs | 0.84× |
| 1000 | 541 µs | 541 µs | **1.00×** |

Two findings, and the second is the uncomfortable one.

**Persisting one streaming event costs 170–540 µs.** The repository's own CI
benchmark agrees independently — `backpressure_append_volume/sqlite_store_502_events`
is 110.02 ms, or 219 µs/event — and that is against 2.83 ms for the same 502
events in memory, a **39× penalty**. At 200 µs/event, an agent emitting 100
events/second saturates a core at roughly 50 concurrent tasks. This is the
dominant cost of any persistent A2A agent built on this SDK, and SQLite is the
store the documentation recommends first.

**The 0.9.0 "incremental artifact persistence" does not deliver an asymptotic
win.** It is modestly better at small documents — which is where it was tuned,
and the code comments say so — and it converges to exactly the full rewrite by
1000 parts. The cause is visible in `artifact_delta_sql`: the statement is
`UPDATE tasks SET data = json_set(data, '$.artifacts[…].parts[#]', …)`, and
SQLite's `json_set` parses and re-serialises the entire `data` document. The
Rust-side serialisation is saved; the database-side rewrite is not, and it is
the larger half.

This is not a bug — the code does what it says. But "incremental persistence"
reads as an order-of-magnitude claim and the measurement does not support one.
A real fix means normalising parts out of the JSON blob into their own
append-only rows, which is a schema change, not a statement change.

**Second-worst, and less alarming:** `transport_jsonrpc_send/single_message` at
194.8 µs on loopback. That is a full HTTP round trip through hyper, and the
`realistic_interceptor_chain` series shows ten interceptors add only ~8 µs, so
the cost is the stack rather than this SDK's logic. It is not a defect; it is
the number to know before promising throughput.

## 4. Worst developer experience

Ranked by how many people hit it.

1. **MSRV 1.93.** Covered above. It is the first thing that stops an
   organisation from adopting, and it now has a 1.85 alternative.

2. **The Quick Start taught a server you could not ship** — fixed in this
   branch. `serve()` accepts forever and returns only if you drop its future,
   which cancels the accept loop and silently kills in-flight connections.
   `examples/deploy-agent` — the example whose entire subject is deployment —
   had to switch to the Axum adapter for `with_graceful_shutdown`. The path the
   README teaches and the path the production example uses were different
   functions, and nothing said so. `Server::bind(..).serve_with_shutdown(..)`
   now closes it.

3. **No CLI.** Evaluating this SDK means writing Rust and compiling. That is a
   real barrier at the "does this work at all" stage.

4. **Compile time.** A cold `--all-features` workspace build is minutes, and the
   test binaries take longer than the tests. Partly inherent to 16 feature
   combinations; still what a contributor feels first.

5. **Ten feature flags on the umbrella crate**, and the SLIMRPC binding is not
   among them — it cannot be, being out of workspace. `a2a-protocol-sdk` is sold
   as the batteries-included entry point and one binding is unreachable from it.

## 5. What misses the production-ready bar

The framing this repository already uses — *supported* and *verified* are
different claims — applied to the operational surface.

* **~~`serve()` cannot drain.~~ Fixed in this branch.**
* **~~`serve()` has no connection ceiling.~~ Fixed** for the new entry point.
  `serve()` and `serve_with_addr()` still spawn a task per accepted socket with
  no bound; the EMFILE backoff handles the symptom, not the cause.
* **No connection-level timeouts anywhere.** There is an `executor_timeout` for
  agent code and request timeouts on the client, but no header-read timeout and
  no idle timeout on the server. A slowloris connection holds a task
  indefinitely. This is the largest remaining hardening gap and it is not
  in the ROADMAP.
* **`serve()`/`serve_with_addr()` discard `serve_connection`'s result**
  (`let _ = …`). A connection that failed to negotiate and one that served a
  thousand requests are indistinguishable. Inconsistent with this project's own
  "make failure paths observable" work in 0.9.0. The new entry point traces it;
  the old two still do not.
* **`serve_with_addr` spawns and returns no handle** — the accept loop cannot be
  joined or aborted.
* **`panic = "abort"` in the release profile.** For binaries built from this
  workspace, any panic — including a poisoned-lock `expect` — takes down the
  whole process rather than one task. Defensible for a CLI, worth an explicit
  decision for a server, and currently it is a workspace default nobody records
  a reason for.
* **Rate limiting is per-process.** Three replicas mean 3× the configured limit.
  The module says so further down; the summary line said "token-bucket" when the
  implementation is a fixed window — corrected in this branch, because a fixed
  window admits 2× the limit across a boundary and anyone sizing against an
  upstream ceiling needs that from the summary.
* **No sustained-load or soak evidence anywhere in the repository.** Criterion
  measures latency at fixed concurrency for seconds. Nothing measures an hour, a
  leak, or a slow degradation. The SLIMRPC README is admirably explicit that it
  has none; the rest of the repository has none either and does not say so.

## 6. Documentation and GitHub Pages

The book is 11,593 lines across 43 pages, live at a2a-rust.com, with search,
themes, canonical URLs, and a sitemap. Structurally it is in good shape. What is
missing is thematic, and it maps almost exactly onto the headline features:

* **No chapter on multi-tenancy.** `TenantResolver`, `PerTenantConfig`, and four
  tenant-aware stores are a headline feature with no page of their own —
  scattered mentions across `stores.md` and `configuration.md`.
* **No chapter on observability.** Same story for `Metrics` and OpenTelemetry.
* **No chapter on security.** SSRF protection, body limits, CORS, path-traversal
  defence and header-injection prevention are spread across `production.md` and
  the API reference.
* **No troubleshooting or FAQ page at all.** Zero occurrences of either word in
  `book/src/`. For an SDK whose failure modes include "wrong `A2A-Version`
  header", "stream ended without a terminal state", and "SPIFFE handshake never
  completes", this is the highest-value missing page.
* **No upgrade guide.** A 0.x that says minor versions may break should tell
  people how to cross one. The CHANGELOG is 191k and is not that.
* **SLIMRPC is filed under "Building Agents"** rather than a bindings section,
  and its book page carries the only structural entry in the ignore-baseline.
* The examples README table lists six of eight examples — `hello-agent` and
  `deploy-agent` are absent from it.

## 7. Examples still to build

The six measured examples each hit 44/44 method×binding cells, and
`incident-response` runs sixteen production-hardening checks. The coverage
*within* the examples is not the gap. The gaps are whole categories:

* **No example uses SLIMRPC.** The binding is out of workspace, so `examples/`
  cannot depend on it — meaning the binding with the most novel operational
  surface (SPIFFE, multicast, fabric nodes) has zero presence in the place
  readers actually look.
* **`multi-lang-team` has no Rust worker.** Python, JS, Go, Java — and the ITK
  now has an obvious fifth language it does not cover: the official Rust SDK.
  Interop with `a2aproject/a2a-rs` is the single most valuable missing ITK leg,
  and it is missing because the SDK did not exist when the matrix was drawn.
* **No durability example.** Nothing demonstrates an agent restarting and
  resuming a long-running task from a persistent store. `incident-response`
  checks that a task survives a handler swap, which is close but is a check
  rather than a narrative.
* **No failure-injection example.** Nothing shows what an operator sees when the
  store is down, the push endpoint is refusing, or the queue is full. The
  `Metrics` hooks for exactly these were added in 0.9.0 and no example reads
  them under fault.
* **No horizontal-scaling example.** Two replicas behind a load balancer sharing
  a Postgres store is the first architecture anyone deploying will reach for,
  and it is where the per-process rate limiter and in-memory event queues stop
  being adequate. Nothing addresses it.

## 8. What misses the engineering-excellence bar

Little does, and it is worth being precise about which little.

* **`send_message_inner` is 526 lines** — measured, the largest function in the
  codebase, on the hottest path, carrying interceptors, extension and streaming
  checks, id and metadata validation, capacity admission, three-phase stale-token
  eviction, and task creation. Already recorded in `.file-length-baseline` with
  an honest note. It is still the one place where a reviewer cannot hold the
  whole behaviour in their head.
* **80 of 409 source files exceed the 500-line guideline.** Ratcheted, so it can
  only shrink — but a fifth of the tree is over the bar the project set.
* **`mutants.toml` was never read by cargo-mutants** (wrong path), so every
  published mutation score includes generated protobuf mutants and ran with a
  328 s budget rather than the 300 s cap the file claims. The ROADMAP documents
  this thoroughly and defers it. It is the one place where a headline number
  measures something other than what it says it measures.
* **Two doc defects found by reading**, both corrected here: the rate-limiter
  algorithm and two stale README figures. Both were in the first line a reader
  sees.

Against that: zero TODOs, 52 panic sites in non-test code across 140k lines,
`#![forbid(unsafe_code)]` everywhere, every gate proven able to fail by
injection, and a ROADMAP that documents its own measurement errors including one
that was wrong by an order of magnitude in the *optimistic* direction. That
combination is rare.

## 9. What I am least confident in

Stated plainly, because the rest of this document is assertive.

1. **Absolute performance numbers.** The SQLite figures were taken on a shared
   cloud VM with unknown I/O characteristics. The *relative* comparison
   (delta vs full save) is sound because the arms were interleaved on fresh
   databases; the absolute µs are indicative. That CI's independent 219 µs/event
   lands inside my 170–540 µs range is corroboration, not proof.
2. **The claim that `json_set` is the cause.** I read the generated SQL and the
   growth curve matches, but I did not profile SQLite itself. The mechanism is
   inferred from two consistent observations, not measured directly.
3. **The official SDK comparison.** Built from its published README, its
   `a2a-slimrpc` 0.2.4 source, and crates.io metadata. I did not build or run it.
   Feature claims from a README are not verified behaviour — the same standard
   this project applies to itself.
4. **Download counts as adoption.** 25,022 is real, but crates.io counts include
   CI, mirrors, and docs.rs builds. It is evidence of reach, not of production
   use, and the gap between those two is unknown.
5. **The 157 ignored tests.** I confirmed they are database-gated and that CI
   provides the service; I did not run them here.
6. **Anything about sustained behaviour.** No soak test was run, by me or by
   this repository, ever. Every statement about stability under hours of load is
   unevidenced — including the optimistic ones.

## 10. What fails the "proudly call it production ready" bar

The parts I would not defend without qualification, in order:

1. **Connection-level timeouts do not exist.** A server with no header-read or
   idle timeout is not one I would put on a public interface without a proxy in
   front, and the documentation does not say to.
2. **No soak evidence.** "Production ready" implies someone ran it for longer
   than a benchmark. Nobody has.
3. **Horizontal scaling is undemonstrated and partly unsupported.** The rate
   limiter is per-process and the event queues are in-memory. A second replica
   changes behaviour in ways nothing documents.
4. **The SLIMRPC binding is published without dependency auditing.** 379
   transitive dependencies, including native crypto, reaching users through a
   crate that `cargo deny` never sees.
5. **Persisted-event throughput.** 39× slower than memory, with the headline
   optimisation not delivering asymptotically. Fine for a control-plane agent,
   not fine for a high-rate streaming one, and nothing tells you which you have.

Everything else — the protocol surface, the conformance evidence, the testing
discipline, the honesty of the ROADMAP — I would defend as-is.

## 11. What I would do differently

* **Decide the MSRV against 1.85, not against a hypothetical.** It is now a
  competitive fact.
* **Ship a CLI.** It is the cheapest adoption unlock available and the official
  SDK has already established the expectation.
* **Bring SLIMRPC inside the gates that matter.** Not the workspace — that
  reasoning is sound — but `cargo deny` and `cargo package` should see it. A
  separate `deny.toml` in the binding directory and a `--dry-run` package step
  are both small.
* **Add the official Rust SDK to the ITK.** It is the highest-value interop leg
  available and the matrix already has the shape for it.
* **Stop optimising SQLite statements and change the schema**, or document the
  per-event cost as a hard number in the stores chapter so readers can size
  against it. The current position — an optimisation whose name promises more
  than it delivers, and no published per-event figure — is the worst of both.
* **Write the troubleshooting page before the next feature.** It is the largest
  gap per hour of work in the entire repository.

# Addendum: what this branch changed

Written after the review above, against the same standard — every claim below
was run on this checkout, and the corrections are corrections of *my own*
findings where measuring more carefully contradicted them.

## Two things I reported that were wrong, both in the optimistic direction

**The SQLite delta path was not converging to parity — it had become a
pessimisation.** The review said delta/save reached 1.00× at 1,000 parts. Run
through `SqliteTaskStore` itself rather than through a hand-written probe, it
crosses 1.0 and keeps going: **1.39× at 1,000 parts and 1.48× at 3,000**. Past
roughly 300 parts, the incremental path was slower than rewriting the whole
record, because it paid a `json_set` parse of the document on top of everything
a full save does. Appended parts now go to an append-only side table, and the
append is flat at ~130 µs from ten parts to three thousand.

**The header-read timeout was not missing — it was silently disabled.** The
review said there were no connection-level timeouts. Hyper *has* one and
defaults it to 30 seconds; it applies only when a `Timer` is installed on the
connection builder, and no server here installed one, so `Time::check` logged
`timeout \`header_read_timeout\` has default, but no timer set` and returned
`None`. Every component was correct and the composition disabled the defence.
That is a worse defect than the one I described, and a different kind: not an
absent feature but an absent line, invisible in every type signature involved.

## Fixed

| Finding | Status |
|---|---|
| SLIMRPC sends no `a2a-version` (§3 MUST) | Fixed — and `validate_version_metadata` is now public, so the server half is fixable from outside the workspace at all |
| SLIMRPC leaks transport keys into A2A headers | Fixed, case-insensitively, taking two keys from `slim_rpc` itself |
| `SlimName::parse` rejects the spec's own bare form | Fixed — bare, `slim://` and `slimrpc://` all resolve to one name |
| 379 published dependencies unaudited | Fixed — `cargo deny` and `cargo package` now run on the binding. **Advisories: clean** |
| No header-read timeout | Fixed — the `Timer` is installed and the timeout is configurable |
| No idle timeout | Fixed — enforced at the socket, counting traffic in both directions so SSE survives |
| Incremental persistence delivers no asymptotic win | Fixed — append is now O(1) in document size |
| Nothing has ever been soak-tested | Fixed — 562,690 requests, 17.0 bytes/request, p95 flat; nightly in CI |

## Where the tests were the problem, not the code

Four tests passed against a defect they existed to catch, and each was found by
injection rather than by review:

* The slowloris test passed with the `Timer` removed — because
  `with_idle_timeout(None)` was a `Duration::MAX` sentinel, `Instant::now() +
  Duration::MAX` panicked in the connection task, and the peer saw a reset in
  94 ms. The disabled path was broken *and* the test passed because of it.
* The same test asserted an outcome ("the read completed") where the property
  is a reason. A connection dropped by a panicking task completes the read too.
* The SSE test never read, so it never reached the deadline check, and passed
  with writes not counting as activity at all.
* Nothing asserted the artifact journal is ever emptied. `splice` skips
  positions the document already holds, so a `save` that failed to clear it
  returns correct tasks forever while the table grows without limit — invisible
  to any test that only checks what comes back.

## Still open

* ~~**Horizontal scaling.**~~ **Closed, and it was mostly not what I said it
  was.** Measured with two handlers over one PostgreSQL
  (`tests/multi_replica.rs`): task visibility crosses replicas, and so does
  subscription *termination* — the reattach hook polls the shared store, so
  §3.1.6 holds across replicas, which I had assumed rather than checked.
  Intermediate events do not cross, which is architectural and now pinned by a
  test. The one real defect was the rate limiter, and
  `RateLimitInterceptor::with_shared_counter` closes it. Two replicas under
  sustained load is now measured too — 64,642 request pairs, 0 failures, 0
  cross-replica misses, 19.2 bytes/pair, p95 flat at 1.04x. See Addendum 3 for
  the two findings that run turned up.
* **MSRV 1.93 against the official SDK's 1.85.** A decision, not a defect.
* **No CLI.**
* **No troubleshooting page**, and no chapter for multi-tenancy, observability
  or security.
* **No example uses SLIMRPC**, and `multi-lang-team` still has no Rust worker.
* **`send_message_inner` is 526 lines.**
* **`mutants.toml` is still at the wrong path.**

# Addendum 2: the horizontal-scaling gap

Called out in the first addendum as "the largest remaining gap". Measured, it
was four separate questions with four different answers, and only one of them
was a defect.

| Claim | Measured | |
|---|---|---|
| A task created on replica A is readable on B | **works** | the store holds it |
| `GetTask` / `ListTasks` span replicas | **works** | same |
| A subscription on B terminates when the task finishes on A | **works** | reattach hook polls the store; §3.1.6 holds across replicas |
| B sees A's intermediate events | **does not** | queues are per-process; architectural |
| The configured rate limit is the deployment's | **did not** | each replica admitted the full rate |

I had reported this as one gap. Three quarters of it already worked, and the
part about subscriptions being spec-compliant across replicas was something I
assumed rather than verified in either direction.

## The fix, and what it costs

`RateLimitCounter` is a one-method trait; `PostgresRateLimitCounter` implements
it with a single atomic `INSERT .. ON CONFLICT DO UPDATE .. RETURNING`. Two
limiters sharing one now admit 5 where they used to admit 10.

The cost is not small and is documented rather than buried:

| Counter | Per request |
|---|---:|
| In-process (default) | 0.2 µs |
| `PostgresRateLimitCounter` | 232 µs |
| The same on a durable pool | 598 µs |

A whole JSON-RPC request through this server measures ~195 µs on the same
machine, so a shared counter roughly doubles a request. The 598 → 232 µs comes
from running the counter's own pool with `synchronous_commit = off` — correct
for a counter describing a 60-second window, and deliberately *not* applied to a
pool passed in via `from_pool`, which is usually the task store's.

When the counter is unreachable the limiter counts locally, so the failure mode
is the per-process behaviour the deployment already had — not an outage, and not
an open door.

## ~~Finding~~ Fixed: `caller_identity` was never set by anything

The rate limiter documents `CallContext::caller_identity` as its first choice of
caller key, "set by authentication interceptors". Nothing set it:

* `ServerInterceptor::before` takes `&CallContext` — an interceptor
  *structurally could not* mutate one;
* no dispatcher constructed a context with an identity;
* `with_caller_identity` had no caller outside tests.

So every caller shared the `"anonymous"` bucket unless `trusted_proxy_hops` was
configured with an `x-forwarded-for` header present. **Per-caller rate limiting
was not per-caller**, and one noisy client spent everyone's budget. It went
unnoticed because every rate-limit test set the identity by hand on a
`CallContext` it had built itself.

The `JwtAuthInterceptor` had already run into this and left a note — it
computed a validated principal and threw it away, `map(|_principal| ())`, with
a comment saying the principal "is available should a future `CallContext` gain
a slot for it". That slot is the fix.

`CallContext::caller_identity` is now a `OnceLock<String>` with
`set_caller_identity(&self, ..)`, so the component that knows who the caller is
can say so through the shared reference it actually has. Write-once rather than
a mutex because identity is established once; two interceptors disagreeing is a
misconfiguration, and the first answer now sticks instead of the last one
silently winning.

Three interceptors supply one. `JwtAuthInterceptor` records the validated `sub`,
which closes its own comment. `ApiKeyAuthInterceptor` and
`BearerTokenAuthInterceptor` record a label when built with
`with_labelled_keys` / `with_labelled_tokens`.

The label is supplied rather than derived from the credential, deliberately: a
caller key reaches a shared rate-limit table, and can reach logs and metrics. A
bearer token belongs in none of those, so hashing it — the obvious shortcut —
would have put credential-derived material in all three.

One ordering requirement falls out, and it fails silently: the chain runs
interceptors in registration order over one context, so a limiter registered
before authentication reads an identity nothing has set yet and buckets every
caller together. Documented on both the module and the struct.

Verified under load: the two-replica soak now authenticates each of its eight
workers with its own labelled key rather than working around the gap with
`x-forwarded-for`, and the counter table holds eight keys across 63,339 request
pairs.

## Finding: the `tasks` table grows without bound

65,399 rows in one minute, and nothing removes them. A2A has no `DeleteTask`
and `PostgresTaskStore` has no capacity eviction — both correct decisions — so
a deployment needs a retention policy it has to supply itself. Nothing in the
repository said so; the horizontal-scaling chapter now does.

# Addendum 4: a flake I wrote, and a CI setting that hid where it was

## The failure

`Test (1.93, macos-latest)` went red on
`serve::graceful::idle::tests::a_slow_but_progressing_peer_is_not_disconnected`:

```
byte 2 should arrive, got: connection idle for more than 75s; closing to
release the task and descriptor
```

The peer had written that byte 15 virtual seconds inside the window, and the
same test had passed on Linux and Windows, on both toolchains, on every run
before it — including 300 consecutive local runs afterwards. It is my own test,
added with the connection timeouts in `b27d400`, so this is a flake the branch
introduced and got away with once.

## Why paused time and a real socket do not mix

The module claimed `start_paused` made these tests immune to a loaded runner.
That is true of the *timers* and false of the *transport*, and the difference
is in tokio's own auto-advance (`runtime/time/mod.rs`, `park_thread_timeout`):

```rust
self.park.park_timeout(rt_handle, Duration::from_secs(0));
if !handle.did_wake() {
    clock.advance(duration);
}
```

The runtime polls the I/O driver with a zero timeout and then jumps the clock to
the next timer **regardless of what that poll found** — `did_wake` belongs to
the *time* handle, so dispatching a socket readiness event does not stop the
advance. A peer's `write` reaching the kernel and the reader learning the socket
is readable are two different moments, and the virtual clock is free to cross
the idle deadline in between. When it does, the reader polls the socket
(Pending, because readiness has not arrived), polls the deadline (expired), and
reports the connection idle. On epoll the event was always there in time; on
kqueue, once, it was not.

The fix is `tokio::io::duplex`, which removes the gap rather than narrowing it:
a write wakes the reader's waker from inside `poll_write`, so the reading task
is on the run queue before the scheduler can consider parking. Five of the six
tests moved; the sixth asks whether `is_write_vectored` is delegated, which only
a real socket can answer, and it does not pause time.

Widening the window instead — a 300-second idle allowance against 60-second
writes — would have made the race rarer and left it in place. A test whose
failure mode is indistinguishable from the defect it exists to catch is worse
than no test, because the first response to it is to doubt the code.

## A sixth test that was the problem, not the code

`end_of_stream_reads_as_eof_not_activity` asserted only the EOF half of its own
name. Making EOF re-arm the timer — the exact defect the guard in `poll_read`
exists to prevent — changed nothing that test could see, because at this layer a
re-armed timer has no observable effect on a read that already returned zero. It
now reads the deadline directly, before and after, and the injection that
proves it is in the set below.

All four gates are proven able to fail:

| Injected defect | Caught by |
|---|---|
| Reads do not re-arm the timer | `a_slow_but_progressing_peer_is_not_disconnected` |
| Writes do not re-arm the timer | `a_write_only_stream_stays_alive` |
| The deadline is never consulted | `a_silent_peer_is_disconnected`, `activity_does_not_buy_permanent_immunity` |
| EOF counts as activity | `end_of_stream_reads_as_eof_not_activity` |

## RUSTSEC-2026-0258, and why the advisory's own fix broke a different gate

The same run went red on both cargo-deny jobs — the workspace's and the

> **RUSTSEC-2026-0258** — h2 accepts and queues empty DATA frames without
> limit. If streams are not actively drained this is unbounded memory growth,
> or a panic if the length overflows. Patched in 0.4.16.

h2 sits under hyper on this SDK's HTTP/2 request path, so it is a real finding

## The semver gate said it was advisory. It has been blocking since 0.7.0

The `cargo-semver-checks` job carried the claim twice — once in its header
("this reports rather than hard-fails until the first 1.0"), once inline beside
`feature-group`, a key that selects features and has nothing to do with
blocking. Neither was implemented. There is no `continue-on-error` in the job,
so every break it found has been a hard failure for as long as the comment has
denied it.

The fix is the comment, not the behaviour, because the premise does not survive
being run. The stated reason for wanting it soft — "on a 0.x baseline a MINOR
bump is allowed to break" — describes a rule cargo-semver-checks already
applies. Measured with 0.50.0 against `a2a-protocol-types`, renaming
`utc_now_iso8601` as the injected break:

| state | exit | verdict |
|---|---|---|
| version unchanged, no break | 0 | no semver update required |
| version unchanged, break present | 100 | semver requires new major version |
| 0.9.0 → 0.10.0, same break | 0 | "(major change)", 254 checks skipped |

A deliberate 0.x break passes the moment the minor component is bumped. What
`continue-on-error` would have bought is already there; adding it would only
buy the rest — a gate that cannot fail. What the job can still fail on is a
break the version does not cover, which is the case worth blocking and the
likely one here: `crates/*/Cargo.toml` reads 0.9.0 and crates.io has 0.9.0, so
between releases the baseline is the version being developed against.

(`--release-type minor` does *not* reproduce the third row — it reports
"requires new major version" for a 0.9.0 crate. Only a real 0.9.0 → 0.10.0 bump
is read as a major change. The override is not a model of the release.)

Worth knowing rather than assuming: `feature-group: default-features` checks
the default surface only, so a break behind `signing`, `grpc`, `postgres` or any
other optional feature is outside what this gate can see. Left as-is and
written down.

## Multi-line `run:` blocks, and one parser instead of two

The last thing neither local harness could see. `gates_for_jobs` read
single-line `run:` only, so ci.yml's three block scalars were skipped in both:
the multi-replica postgres suite, the SPIRE install, and the SPIFFE suite.

Block bodies are now emitted as one `bash -e -c $'...'` command — one physical
line because every consumer is line-oriented, ANSI-C quoted rather than joined
on `;` because two of the three are a single logical command split by a
backslash continuation, where `;` would make two broken commands out of one
working one.

`bash -e`, deliberately not `-eo pipefail`. That is the shell GitHub gives a

### Three bugs in the above, all mine, all found by testing rather than reading

**The quoting.** gsub applies its own backslash rules on top of the string
literal, and the two layers together turned one backslash into six. Rebuilt a
character at a time.

**The guard that checked nothing.** `require_known_skips` iterated
`printf '%s' "$SKIP_STEPS" | tr '|' '\n'` with `while read`. No trailing
newline means `read` returns non-zero on the final line, so the body never ran
for the last alternative — and with a single exemption, that is every
alternative. The guard executed and verified nothing. Found by handing it a
deliberately stale pattern and watching it pass.

**Folded scalars.** The rule matched `run: [|>]` and treated both alike. YAML
folds `>` by joining lines with spaces, so `run: >` / `echo one` / `two` means
`echo one two`; the parser would have emitted two commands, the second of which
does not exist. Confirmed against PyYAML rather than assumed. Folding is
implemented now — see below; the first fix for this was a refusal, which was
the wrong shape of answer.

## Folding, implemented rather than refused

The first response to the folded-scalar bug was to make `gates_for_jobs` refuse
`run: >` and say so. That is defensible — a gate running the wrong command is
worse than a missing one — but it is still a hole with a sign on it, and the
sign said "someone else decide". So `>` is now folded properly:

* a break between two ordinary lines folds to a single space;
* empty lines are not folded away — k empty lines between content become k
  newlines, and the fold-space is dropped;
* a **more-indented** line is kept literally, and the breaks on either side of
  it stay newlines;
* an explicit indentation indicator (`>2`, `|2`) sets the block indent instead
  of inferring it from the first non-empty line, which is the case it exists
  for.

Chomping (`-`, `+`) is parsed and deliberately not acted on: it changes only
how many line breaks end the scalar, and a trailing newline cannot change what
a shell command does. Said out loud here rather than left as an accident.

The more-indented rule cost a second bug. Getting it right for a bare indented
continuation is easy; what is not obvious is that a blank line *before* one
contributes its newline **and** the unfoldable break survives — one blank line
before an indented continuation is two newlines, not one. That was wrong in the
first implementation and neither reading the spec nor reading the code found
it.

What found it was `scripts/check_block_scalars.py`, which is now a CI gate: 22
block-scalar shapes, each parsed by the awk and by PyYAML, compared. It is a
differential test rather than a table of expected strings on purpose — the
expectations come from an implementation that is already right, so the test
cannot inherit the author's misreading, which is exactly how the bug survived
being written and reviewed.

`bash` decodes the `$'...'` quoting in that check rather than the checker
re-implementing it, so the emitter is tested against the shell that will
actually run it and not against a second copy of its own logic.

Proven able to fail, by widening the fold separator to two spaces in
`ci_gates.sh` and watching every folded case go red: `1 proven, 0 unproven`.
The injection breaks folding rather than the checker, because the gate exists
to notice a parser regression.
