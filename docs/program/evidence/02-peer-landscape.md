# 02 — Peer landscape: a2a-rust against a2a-rs, the official SDKs and the swarm stacks

Date of research: 2026-11-25. Read-only. Nothing under `/home/user/a2a-rust` was modified and no cargo build was run.

Conventions used throughout:

- **VERIFIED** — I read the file or ran the command named. Clone paths are relative to `U = UPSTREAM`. a2a-rust paths are relative to `/home/user/a2a-rust`.
- **INFERRED** — concluded from evidence that does not state it directly (most often: a term search with no hits).
- **NOT FOUND** — searched and absent; the search is stated.
- `gt <dir> <regex>` means: `grep -rIilE <regex> <dir>` excluding `.git`, `node_modules`, `target`, lockfiles and changelogs. A zero from `gt` proves the word is absent, not that the capability is; where that distinction matters I say so.

Limits of this research, stated once:

- The GitHub API was not available (`gh api` returned 403 for every a2aproject repo), so open pull requests and issues were **not** inspected. v1.1 status comes from remote branch lists (`git ls-remote --heads`) and fetched branch tips only.
- `microsoft/agent-framework` could not be cloned (`fatal: could not read Username`); it and LangGraph Platform (closed-source server) are covered from documentation only.
- The swarm stacks were examined at their A2A integration modules, not their whole codebases. Their rows are shallower than the SDK rows and are labelled accordingly.
- No performance measurement was made here. All performance figures are quoted from the repository's own 2026-11-11 document.

## 2. Things peers have that a2a-rust lacks or does worse — ranked by adopter impact

1. **A2A 1.1 is not started here, and the official Rust SDK has a complete stack for it.** VERIFIED. Upstream tagged `v1.1.0-rc` on 2026-10-29 and `dev-1.1` moved on 2026-11-24 ("add timestamps across the task model"). a2a-rs carries eight stacked branches (`a2a-1.1/1-baseline` through `8-live-examples`, tips 2026-11-12) with `SendLiveMessage` on gRPC, JSON-RPC and REST, generation and timeline fields, live examples, tests (`a2a-server/tests/live_message.rs`, `live_message_races.rs`, `multi_client_live.rs`) and a `MIGRATION.md`. a2a-python has 1.1 types and task-generation branches from 2026-11-24. a2a-rust's position is an unmade decision (`ROADMAP.md:54-59`). Impact: the upstream roadmap names bidirectional streaming and "handling agent messages received during working states" as near-term (`A2A/docs/roadmap.md`). Those overlap directly with two of a2a-rust's private extensions — steering (`https://a2a-rust.com/extensions/steering/v1`) and the WebSocket binding. When 1.1 ships, a standard mechanism will exist for what a2a-rust does privately, and the official Rust SDK will speak it first.

2. **Raw server throughput: a2a-rs is faster, and the gap widened after 0.14.1.** Quoted from `docs/sdk-comparison-2026-11-11.md`, not re-measured:
   - a2a-rs serves 1.25 to 1.9 times a2a-rust's blocking-send throughput at every concurrency tested: 1.8–1.9× at one connection, 1.25–1.3× at 16–256 (line 110-112). Example cells: 7,960 vs 4,228 requests/s at one connection; 9,821 vs 7,790 at sixteen (table 1).
   - a2a-rust regressed against its own 0.14.1: 4.3k vs 6.1k requests/s at one connection, non-overlapping ranges (line 113-117).
   - On one core at sixteen connections a2a-rs is about twice as CPU-efficient per request: 52 vs 104 µs (table 3).
   - In a2a-rust's favour: 2.5–3× less resident memory (64–98 MiB vs 150–230 MiB), and a2a-rs "as shipped" has no `TCP_NODELAY`, making streaming about 44 ms per request (still true: `grep -rn -i nodelay --include=*.rs a2a-rs` = 0).
   - **Stated leads** (lines 128-177): (i) per-request timer arming — the header-read timer from `ServeConfig` (ADR 0042) and a `tokio::time::timeout` in `streaming` each wake the I/O driver; VALIDATED as the source of the extra wake-ups, CONJECTURED as most of the two-core gap; not fixed because the header timer is a slowloris defence, so the lead is "a cheaper way to bound a header read". (ii) ~36 KB futures moved by value through four wrapper layers per spawn; boxing landed, gain within noise. (iii) allocation ≈ 25% of self time, a SipHash map ≈ 4%; unattributed remainder. (iv) Not measured: HTTP+JSON, gRPC, WebSocket, `default-features = false`, 64/256 connections after the change.
   - With a real model in the loop the gap is not observable (table 5). So this matters for gateways, routers and high-fan-out coordinators, not for a single LLM-bound agent.

3. **Distribution and official standing.** VERIFIED. a2a-rs is the SDK named on a2a-protocol.org (`A2A/docs/sdk/index.md`, `docs/sdk/rust.md` added 2026-11-24 — the spec repo's HEAD commit). Its CLI is published with Homebrew, WinGet and an install script. a2a-rust's CLI is `publish = false`. The official Go `a2a` CLI has a coding-agent plugin marketplace, contacts, AI Catalog lookup and transport plugins (`a2a-cli/README.md`). An adopter choosing "the Rust SDK" from the protocol site never sees a2a-rust except in the community list, where it is labelled v1.0.0.

4. **v0.3 compatibility.** VERIFIED. Python, Go, JS, Java and .NET each ship a 0.3 compat layer (paths in matrix). a2a-rust's server refuses a request with no `A2A-Version` header by default. In a polyglot fleet with older agents, a2a-rust is the node that cannot talk to them. (a2a-rs shares this gap.)

5. **Interactive OAuth on the client.** VERIFIED. a2a-go 2.9.0 added `a2aclient/oauth`: discovery from agent cards and Protected Resource Metadata, authorization-code and device grants, token refresh as a plugin. a2a-rust has client-credentials and RFC 8693 exchange but `grep -rIl -i 'device_code\|authorization_code\|pkce' crates/a2a-protocol-client/src` = 0. This matters for any agent acting for a signed-in human.

6. **Registry and catalog discovery.** VERIFIED absent here (`ai-catalog` = 0 hits repo-wide; decision recorded at `docs/swarm-orchestration.md:290-292`). Peers and the ecosystem are converging on catalogs: the inspector and CLI read AI Catalogs; AGNTCY has a directory with an IETF draft; Google has an Agent Registry and the ARD spec; .NET documents service discovery. a2a-rust's fleet discovery is mDNS (link-local) plus a card cache. Across subnets, clusters or organisations an adopter supplies the registry.

7. **A plugin model that spans client, server, executor, store and push in one object.** VERIFIED in a2a-go (`a2aplugin/`, `CHANGELOG.md` 2.9.0), a2a-python (`src/a2a/plugins`), a2a-js (`docs/plugins.md`, "no runtime dependencies … including Cloudflare Workers"). a2a-rust has separate interceptor traits, `Metrics`, `AuditStore` and others; `grep -rIl 'trait .*Plugin' crates/*/src` = 0. One-object cross-cutting extensions are what third parties package and share.

8. **Coding-agent bridge (ACP executor) and a fleet demo that visibly survives crashes.** VERIFIED. a2a-go's `a2aacp` and the `opencode-fleet` sample ("Kill a server mid-conversation: the agent's memory, its files and its pending questions continue on another server") are a ready demonstration of a fleet. a2a-rust has no ACP bridge (`agent client protocol` = 0 hits in crates/examples/tools/book). Its replica story (0.16 turn claims) is arguably stronger as a library feature, but there is no equivalent one-command demo found in this pass (INFERRED; `examples/swarm` and `deploy/` were not run).

9. **Collaborative-task extension and SLIMRPC as first-party.** VERIFIED. a2a-rs has `a2a-collab` on a branch (2026-11-23) for shared/collaborative tasks, with extension URIs under `a2a-protocol.org/extensions/…` — upstream-namespaced, unlike a2a-rust's `a2a-rust.com/extensions/…`. a2a-rs's SLIMRPC crate is in-workspace and has a Go-CLI transport plugin.

10. **MySQL**, **edge runtimes**, **Android HTTP client**. VERIFIED present in peers (`pyproject.toml` `mysql`; a2a-js Cloudflare Workers; `a2a-java/extras/http-client-android`), absent here (`grep -rIl -i mysql crates/*/Cargo.toml` = 0). Low impact for a Rust audience.

11. **Browser inspector.** VERIFIED. `a2a-inspector` is a single Go binary with traffic log, card editor, host agent. It works against a2a-rust agents too, so this is not a gap in capability, only something not to rebuild.

## 4. DevEx patterns worth adopting

Each is concrete and taken from a peer file.

1. **One call from "agent" to "served agent".** ADK: `a2a_app = to_a2a(root_agent, port=…)` returns an ASGI app, generating the card from the agent (`adk-python/src/google/adk/a2a/utils/agent_to_a2a.py:78-96`; used at `contributing/samples/a2a/a2a_root/remote_a2a/hello_world/agent.py:110`). MAF: `app.MapA2A(agent, path, card)`. a2a-rust's shortest path is `agent_executor!` + `AgentCard::new…` + `RequestHandlerBuilder` + `Server::bind` + `serve_with_shutdown` (README lines 189-208). A `serve(agent, addr)`-shaped helper that derives a default card would match the peers' first-contact experience.
2. **Serve a script or a coding agent as an A2A agent from the command line.** Official CLI blog: "an A2A server built from an ordinary script with `--exec`"; `a2a-serve` "serves Claude Code, opencode or any ACP coding agent as an A2A agent" (`a2a-cli/README.md:56`). For swarms this is how workers get onboarded without writing an executor.
3. **Publish the CLI.** a2a-rs ships `a2acli` via crates.io, Homebrew, WinGet and a curl installer; a2a-rust's is unpublished. The official CLI's scripting contract (JSON output, distinct exit codes) is already mirrored by a2a-rust's tool (`README.md:380-383`); it only lacks distribution.
4. **A single plugin object across client, server, executor, store and push**, with a global or per-instance registration (`a2a-python/src/a2a/plugins/__init__.py:1-13`; `a2a-js/docs/plugins.md`; `a2a-go/a2aplugin`). a2a-rust's swarm controls are already cross-cutting; packaging them as one installable unit is also the natural shape for the "middleware for other SDKs" item (`ROADMAP.md` Fleet §14).
5. **A cluster-mode sample that proves itself.** a2a-python: `python -m samples.clustermode.run_cluster --replicas 3` then `exercise` prints "OK: one task was started, observed, and cancelled across three different replicas" (`samples/clustermode/README.md`). opencode-fleet: `make kill S=server-2`, `make join`, `make drain` with a live `watch` view. a2a-rust has the mechanism (0.16 turn claims) and should have the equally short proof.
6. **Metadata/header propagator as a pair of interceptors** (`a2a-go/a2aext/propagator.go:83-116`): a server interceptor captures allow-listed keys, a client interceptor re-emits them on outbound calls. This is the generic form of what a2a-rust does per extension, and it is the smallest thing another SDK needs to *carry* a2a-rust's lineage, budget and lease through a foreign hop.
7. **Structured-input extension with typed request/response helpers** (`a2a-go/a2aext/structuredinput`), aligned with the upstream "Elicitation" roadmap item. a2a-rust's approval extension is the nearest analogue; aligning shapes early avoids a second private dialect.
8. **Migration CLI for stores** (`a2a-js` `a2a-db` bin; a2a-python `db-cli` extra with Alembic). a2a-rust migrates on open; an explicit, inspectable migration command is what operators of shared Postgres expect.
9. **Behaviour manifest for conformance** (`acts/sut-behaviors.yaml` in every official SDK, a2a-rust included). Already adopted; noted because it is the shared convention to keep.
10. **A per-release `MIGRATION.md` written alongside the change stack** (a2a-rs 1.1 branches). a2a-rust has upgrade guides in the book; the pattern to copy is writing it as part of the stack rather than after.

## 6. Assessment of the thesis

> "Other stacks need multiple components and glue code on top of their A2A SDK to run agent swarms/fleets; a2a-rust has that built in."

### Where it is true

- **For the control plane of a delegation tree, it is true and the evidence is strong.** Lineage, cascade cancel, halt, hop-shrinking budgets, parent→child leases, a delegation journal with reattach, RFC 8693 actor chains, a hash-chained audit log, an admission gate and client-side balancing with ejection and hedging are all in a2a-rust's crates (section 3, with file references). None of the six official SDKs has any of the first six. The orchestration frameworks examined (ADK, CrewAI, Strands) do not even send `CancelTask` to a remote agent from their A2A client modules. An adopter on any of those stacks who wants "stop the root and everything under it stops" writes it themselves, per hop.
- **For "one dependency instead of SDK + proxy + identity service + registry + OTel wiring", it is true in the narrow sense of component count.** What agentgateway supplies at a proxy (retries, outlier handling, rate limits, token exchange, tracing), a2a-rust supplies in-process.

### Where it is false or overstated

- **"Built in" is true only between a2a-rust nodes.** Every swarm control travels as a private extension under `https://a2a-rust.com/extensions/…` (nine URIs found). The project's own ADR 0049 says a non-Rust peer receives lease, budget, idempotency key, failure class, approval and provenance and **ignores them**, halts never cross, and cancel crosses one hop. In a polyglot fleet — which is what A2A exists for — a2a-rust adopters need glue too: middleware in each other SDK (`ROADMAP.md` Fleet §14, not built). The thesis as worded compares a2a-rust's homogeneous case with everyone else's heterogeneous case.
- **Fleet discovery is not built in.** mDNS and a card cache are not a registry; the project decided not to build one. Peers reach for a directory or catalog; so will a2a-rust adopters beyond one LAN.
- **The planning half of a swarm is not here by design** (`docs/swarm-orchestration.md:14-18`: "what makes that work — planning, judging … lives above A2A"). ADK, LangGraph, CrewAI and MAF *are* that half. An a2a-rust adopter assembles a2a-rust + a model client + an orchestration loop; the repo's own `tool_loop` covers one agent's loop, and `examples/swarm` "stays an example". So "others need multiple components" applies to a2a-rust as well, at a different seam.
- **For replica fleets of one agent, peers are no longer behind.** a2a-python, a2a-go, a2a-java and a2a-js all have shared-store or cluster modes, and a2a-go's opencode-fleet demo is more persuasive than anything found in this repo in this pass.
- **Several controls have known open cases in the project's own roadmap**: reattached-delegation hand-off, the steering dead-replica window, multi-host qualification, "60 replicas at once", SQLite delegation journal (`ROADMAP.md` Fleet §4, 8, 9; `docs/swarm-orchestration.md:70-71`). "Built in" should be read as "implemented and tested on one machine", per the project's own qualification notes.

### The strongest counter-case

A platform team in late 2026 would argue the following, and each step is supported by evidence above:

1. The standard is moving (1.1 RC, bidirectional streaming, AAIF governance), and the official Rust SDK already has a 1.1 stack while a2a-rust has not decided to start. Building a fleet on private extensions of a 1.0.1 SDK is a bet against the standard's direction on exactly the features (mid-task messaging, live streams) the standard is about to cover.
2. Cross-cutting policy belongs in infrastructure they already operate: a gateway for balancing, ejection, rate limits and token exchange (agentgateway is Rust, Linux Foundation, A2A-aware); the cloud's identity service for OBO; a catalog for discovery; the OTel collector for tracing. Those work for *every* language in the fleet. In-process equivalents work only for the Rust nodes and must be configured per binary.
3. The official Rust SDK is 1.25–1.9× faster on the wire-level benchmark, is one-seventeenth the code to audit in its server crate, and is the one listed on the protocol's site.
4. What remains genuinely missing everywhere — lineage, cascade, budget, lease — is small enough to write as middleware once (a2a-go's propagator is ~200 lines) and is exactly what should be standardised upstream rather than adopted from one community SDK's namespace.

On that reading, a2a-rust's differentiated value is not "has it built in" but "has **designed, measured and specified** the four controls nobody else has" — and the durable way to realise that value is to get them out of the `a2a-rust.com` namespace: upstream proposals, conformance vectors (lineage already has them), and thin middleware for a2a-python and a2a-go. The thesis is defensible as "a homogeneous Rust fleet needs no additional control-plane components"; it is not defensible as a general claim about fleets over A2A.

### One-line verdict

**True for control of a single-SDK delegation tree; false for polyglot fleets, for discovery, for orchestration logic, and increasingly false for replica scaling — and it currently trades away standard-tracking (1.1) and throughput to get there.**
