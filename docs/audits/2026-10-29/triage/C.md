## 2. Decisions needed

**C-08: fatal vs warn-and-ignore for unrecognised `OTEL_*` enum and number values.**
1. Keep fail-fast (today). Loud at deploy, matches Java's autoconfigure and the library's own tests/docs; deviates from the spec's "warn and gracefully ignore" [spec-memory] and one stray fleet-wide variable crash-loops every pod and every `a2a` CLI subcommand.
2. Warn-and-fall-back for enum variables (exporter list, protocol, compression), keep errors for TLS, files and headers, using the existing `Telemetry::notices()` channel. Spec-aligned and cheap; a typo is no longer fatal, so it needs the notice to be visible (it is printed by `install_subscriber`).
3. Default lenient plus `TelemetryBuilder::strict()` for binaries that want fail-fast. Most flexible; one more knob.
Recommendation: option 2 for the three enum variables now; revisit numbers (timeout) later. Pair with N-C-8 so the sampler typo is reported the same way.

**C-10: baggage and `OTEL_PROPAGATORS` on the A2A wire.**
1. Document only: say the wire is `traceparent`/`tracestate` regardless of `OTEL_PROPAGATORS`. Zero risk, leaves the gap.

- **N-C-1 (medium): C-11 is only half fixed; the client card resolver still logs raw URLs at INFO.** `a2a-protocol-client/src/discovery.rs:255` `trace_info!(base_url, "resolving agent card")` and `:451` `trace_info!(url = %self.url, "resolving agent card (cached)")`, while the same fetch's span deliberately drops userinfo and query (`discovery/card_span.rs:14-17`: "where a card URL behind a gateway may carry a key").
