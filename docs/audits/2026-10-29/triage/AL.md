## 3. Decisions needed

**D-AL-1 (A14a + A22b): variable names in deploy-agent.**
- Option 1: keep `PORT`/`DATABASE_URL` (what platforms inject) and add one table of every example's variables. Cheap, but a shell that exports `DATABASE_URL` still connects to that database.
- Option 2: rename everything to `A2A_*` across all binaries. Consistent, but touches every README and the manifest, and `PORT` is injected by platforms.
- Option 3: in deploy-agent only, read `A2A_DATABASE_URL` instead of `DATABASE_URL`, and warn when `DATABASE_URL` or `A2A_BIND_ADDR` is set but ignored.
- Recommendation: option 3, plus the table. It removes the collision, costs a rename in the manifest, two READMEs and `scripts/live/replica`, and the example is not public API.

**D-AL-2 (A15d): should readiness probe the push-config store?**
- Option 1: no; document that `/ready` answers for the task store only and why.
- Option 2: add `PushConfigStore::health` with a default `Ok(())` and call it in `readiness()`.
- Option 3: share one pool, so one probe covers both.
- Recommendation: option 1. A push-pool failure should not drain a replica that can still serve sends. State it in `RequestHandler::readiness`'s rustdoc and the deploy-agent README.

**D-AL-3 (A19b): reproducibility of the runtime image's apt layer.**
- Option 1: pin `ca-certificates=<version>`; breaks when Debian retires that version, needs a bot.
- Option 2: apt from snapshot.debian.org with a dated source; reproducible, heavier.
- Option 3: drop apt from the runtime stage and `COPY --from=build /etc/ssl/certs/ca-certificates.crt`, so the final image is determined by two digests.
- Recommendation: option 3, after checking that the digest-pinned `rust:1.94-bookworm` ships the bundle (I did not check) and that `SSL_CERT_FILE=/etc/ssl/certs/ca-certificates.crt` (documented) still resolves.

**D-AL-4 (A24): a ready-to-run server binary or image.**
- Option 1: none; deploy-agent stays the template and containers.md says so (today).
- Option 2: publish deploy-agent as a smoke-test image.
- Option 3: an env-configured `a2a-gateway` (ToolLoopExecutor over OpenAiChatModel) with a published image.
- Recommendation: option 1 now. No release can be signed yet (packaging/README.md:22-24) and nothing is published; options 2-3 add a supported-artifact burden. Revisit after the signing key and an image pipeline exist.

**D-AL-5 (L11): short-lived clients on the client dashboard.**
- Option 1: guidance only. Put the caveat in the client-dashboard section of dashboards.md, and say what to do (run the batch job through a long-lived Collector; use a stable `service.instance.id`).
- Option 2: ship a batch-oriented Collector config (`cumulativetodelta`, drop `service.instance.id`, `deltatocumulative`) and verify it live with `check_dashboards.py`.
- Option 3: have `Telemetry` export a zero sample at start so a one-shot process has two samples (SDK change).
- Recommendation: option 1 now. Note that the audit's suggested `increase()` rule does not help alone: `increase()` over a one-sample series is also empty, so a Collector step is needed anyway (option 2) before any rule can work.

## 4. New findings

- **N-AL-1** (low, observability/security) `redacted()` (examples/deploy-agent/src/main.rs:173-181) removes a password only from `user:pass@host` userinfo. A URL with `?user=u&password=p` has no `@`, falls to `_ => url.to_owned()` and is logged in full at INFO (main.rs:208, and in the error strings at :221,:231). sqlx-postgres 0.9.0 accepts `password` as a query parameter (options/parse.rs:88). Fix: also mask `password=` query values; test: add the case to `the_logged_database_url_has_no_password` (tests.rs:215). S.
- **N-AL-2** (low, docs/security) The Secret recipes at examples/deploy-agent/README.md:105 and book containers.md:81-82 omit `sslmode`, while the manifest comment (deployment.yaml:102) and book examples/deploy-agent.md:189 include `sslmode=verify-full&sslrootcert=...`. sqlx's default is `prefer` (options/mod.rs:211), which does not verify the server. A reader following containers.md gets an unverified connection. Fix: make the three recipes identical. S.
- **N-AL-3** (info, docs) Stale statements: README.md:271 "a `0.0.0.0` bind, a two-stage container", examples/deploy-agent/README.md:82 and book examples/deploy-agent.md:142 "Two stages", ROADMAP.md:340 "two-stage `Dockerfile`". The Dockerfile has three build stages plus runtime (Dockerfile:12), and main.rs:248-253 `bind` listens on `[::]` with `0.0.0.0` as the fallback.
- **N-AL-4** (low, observability; adjacent to L11) `A2AAgentSilent` (critical, a2a-alerts.yml:98-113) fires 10 minutes after the last export of any job and stays firing for a day, and `A2AAgentInstancesLost` (:115-120) compares instance counts an hour apart. A job made of short-lived processes (the `a2a` CLI, a cron client) triggers both whenever it is idle for 10 minutes. dashboards.md's alert table and walkthrough do not say these alerts are for long-lived services. Fix: document, or exclude by a `job` matcher. S.
- **N-AL-5** (low, deploy-assets) No workflow builds `examples/deploy-agent/Dockerfile` or validates `deployment.yaml`: `rg -i 'docker|kubeconform|kubectl|hadolint' .github scripts` finds only the ITK images in acts.yml:60-67 and itk-nightly.yml:84-95. The fixes for A8, A9, A12 and A19(d) therefore rest on one-off manual runs. Fix: a CI job running `docker build` on the file, and `kubeconform` on the manifest. M.
- **N-AL-6** (low, client resilience/ergonomics) `ClientError::HttpClient` and `ClientError::Timeout` never carry the endpoint (crates/a2a-protocol-client/src/transport/jsonrpc.rs:271, rest/request.rs:198, transport/mod.rs:88-99). A caller with several agents (the CLI after a card redirect, Delegation) cannot tell from the message which one failed. Whether hyper-util's own chain text names the host I did not run. Fix: prefix the endpoint in these constructors; adds a string change to error messages (not a type change). S.
- **N-AL-7** (suspicion, stores-sql) The creation guards use `to_regclass('<name>')` (store/pg_schema/mod.rs:137,201), which PostgreSQL resolves through the whole `search_path`. With `search_path=a2a,public` and an application `tasks` in `public`, the guard would see "exists" and skip creating `a2a.tasks`, defeating the dedicated-schema workaround for A14. Premise is PostgreSQL semantics I did not run. Fix: qualify with `current_schema()`; test: live-PG, two schemas.
- **N-AL-8** (info, deploy-assets) `DRAIN_DELAY_SECONDS` accepts any `u64` (main.rs:144-150) and is not checked against the 60 s `terminationGracePeriodSeconds` the manifest sets, whose comment (deployment.yaml:33-43) says the grace period must exceed the shutdown budget. A value of 60 or more guarantees a SIGKILL before the drain finishes. Fix: refuse a value above a documented bound, or log the computed budget at startup. S.
