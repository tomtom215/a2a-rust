## 2. Decisions needed

**D-05 (a),(c): how durable and how smart should webhook delivery be?** Spec §4.3.3 requires one attempt per config, so today's behaviour is conformant.
1. Document only (delivery.md: best-effort, in-memory, lost on restart, reconcile with `GetTask`). S, no risk, does not help a receiver that was down for 60 s.
2. In-memory hardening: a delivery-id header plus a per-URL consecutive-failure breaker that still probes periodically (keeps the MUST). M, no schema, still lost on restart.
3. Durable outbox in the SQL stores (new migration, worker, backoff over hours). L, real at-least-once, new operational surface.
Recommendation: 1 now, plus the delivery-id header (D-05b, S, additive); build 3 only when a deployment asks for it, and 2's breaker with it.

**D-10 (a): what to do with a `Retry-After` larger than `max_backoff`?** Today it is clamped to 30 s, documented and pinned by a test, so a 120 s penalty window is retried three times inside itself.
1. Keep the clamp, add jitter. S, no behaviour surprise, still retries early.
2. Honour it up to the parser's 1 h ceiling. S, but one call can hang for up to an hour times the retries.
3. If it exceeds `max_backoff`, stop retrying and return the error with `retry_after()` readable, so the caller schedules. S, fail-fast, changes what existing callers see on long penalties.
Recommendation: 3, with jitter on the shorter case (D-10b).

**D-11: retries and stream resume.** (a) Retries off by default is right for non-idempotent sends (retry.rs refuses to re-send `SendMessage` blindly), so I would not change it.
1. Status quo plus a book page on the manual resume loop (already in methods/tasks.rs docs). S.
2. Opt-in resume: `RetryPolicy::with_stream_resume(n)` or `EventStream::resuming(client)` that calls `subscribe_to_task_from(last_event_id)` with its own, longer budget than the 3.5 s connect backoff; `follow_task` uses it unconditionally (D-11c). M, additive.
3. Resume by default on every stream. L, changes what `next()` can return (replays, ordering), risky.
Recommendation: 2; do the `TaskFollow` part (c) regardless.

**D-18: in-memory capacity eviction of live tasks.** Documented as a last resort; the dev/test default store only (production uses the SQL stores).
1. Keep, add a metric and warn per non-terminal eviction. S.
2. Never evict non-terminal tasks; refuse new tasks with `Overloaded` when full of live work (as idempotency keys already are). M, makes the cap a hard brake, can surprise a dev who forgot to size it.
3. Evict in tiers: terminal, then `working`/`submitted`, then interrupted (`input-required`, `auth-required`) last. S.
Recommendation: 3 plus 1: parked tasks are exactly the ones nothing re-saves.

**D-20: liveness bounds on by default for gRPC and WebSocket.** Today off, deliberately ("choosing an interval is choosing their traffic profile"), pinned by a test.
1. Keep opt-in; add the numbers to the deploy guide. S.
2. Default on: gRPC HTTP/2 keepalive (60 s, 20 s) and WS idle 120 s (ping at half), each with a `without_*` opt-out. S, additive API, drops peers that never answer PING/Pong.
3. Default on only through `Server`/example helpers. S, leaves library users exposed.
Recommendation: 2, matching the HTTP listener's 75 s stance; flag it in the changelog as a default change.

**D-21 (b): hand a running task to another replica on shutdown.** Not a regression: a crash does not resume either (reaper: `failed`, not resubmitted, because what the executor already did is unknown).
1. Keep: shutdown ends the turn `Failed` transient (done), and tune `completion_grace` per deployment; add a sentence on it to the book.
2. Hand-off mode: stop the executor without a terminal write, release the claim, let another replica resume. L; needs a resumable-executor contract and idempotent side effects.
3. Raise the default completion grace (for example 25 s). S, trades a longer deploy for fewer cut turns.
Recommendation: 1; revisit 2 only together with a resumable-executor trait.
