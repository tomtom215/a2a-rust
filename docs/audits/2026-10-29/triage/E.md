## 2. Decisions needed

**E-F12 (tenant `max_concurrent_tasks` is per replica).**
- A. Document "per replica; divide by replicas" in the rustdoc, multi-tenancy.md and the horizontal-scaling table. S, no behavior change.
- B. Count live claims for the tenant in `a2a_task_claims` at admission under an advisory lock. M, one more round trip per send, only works for tenant-aware stores (a plain store's claim scope is `""`), and is still soft under races.
- C. A new `TenantSlotStore` trait with a PG implementation. L.
- Recommendation: A now. B only if a user asks for a fleet-wide cap; say so in the docs.

**E-F13 (`Profile::Production` accepts per-process halt and lease stores).**
- A. Refuse an in-memory halt/lease store only when the task store is shared (`turn_claims().is_some()`), via defaulted `is_shared()` methods that `InMemory*` override. The book example at `production.md:82` and the profile test keep building (in-memory task store). Small, rarely surprising.
- B. Refuse them always under Production. Breaks the book example and every single-replica Production user.
- C. Warn at `build()` only. No behavior change; the footgun stays but is visible.
- Recommendation: A, with an explicit opt-out for a deliberate single-replica fleet behind a shared database. Handle the rate-limit counter and audit store the same way later (they are not required by any profile today).

**E-F25 (idle reattach polling is unbounded and shares the claim pool).**
- A. Keep the default (spec 3.1.6), document the per-stream cost (about 8 queries/s with a log, 4 without) and tell operators to size the pool or set `subscribe_max_idle`. S.
- B. Back off the poll for a stream that has been idle (250 ms growing to 2 s over a minute). Cuts load about 8x; adds up to 2 s before a continuation's first event reaches a subscriber on another replica. S-M.
- C. `LISTEN/NOTIFY` wake-ups on log append plus a slow safety poll. L; needs a non-pooled connection per replica, as the halt store does.
- Recommendation: A and B now (B behind a `HandlerLimits` knob with the old 250 ms as its floor), C later.

### E-F8 (conjecture in the README)
Reading settles the mechanism. Chain: the writer assigns `seq` and broadcasts (`in_memory.rs:696`); the processor logs afterwards, and a fenced append only logs a warning (`background/mod.rs` `record_event`); `lose_claim` writes nothing and notifies no reader; B's `resume_after` returns `max(last_event_seq, applied position)`, neither of which moved. A's reader on `Closed` reattaches with `after = replayed_through` (`in_memory.rs:1625`), the last id it delivered, and the hook returns `Logged { through }`, replaying only `after+1..=through`. One in-flight event (the existing test's "at most the one write already in flight") is enough to reuse a position. The invariant "no position names two events" is documented for failed appends (`admission.rs:245-252`, `store/applied.rs:61`); a fenced append is the same hole and is not covered. Not shown by reading: how often a real subscriber sits on the loser.
Probe for a person with PostgreSQL 17 and toxiproxy (layout of `scripts/live/partition_live.py`): start `n1` through `pg_a` and `n2` through `pg_b`; `send(N1, "tick", now=True)`; attach `curl -N` to `SubscribeToTask` on N1 and keep its `id:` lines; cut `pg_a` for 20 s; at +16 s `send(N2, "more", task)`; restore; then `SELECT seq, payload FROM task_events WHERE task_id='<id>' ORDER BY seq`. Bug present if an id N1's subscriber saw is a different event than the row at that `seq`, and a resubscribe to N1 with `Last-Event-ID: <highest id>` never receives N2's events at lower ids.

### E-F9 (conjecture in the README)

### E-F11
Fixed since the report: `8a31cf7`, README row A11. All DDL goes through `pg_schema::apply`; a `CREATE INDEX IF NOT EXISTS` / `CREATE TABLE IF NOT EXISTS` / `CREATE OR REPLACE FUNCTION` runs only if the object is missing (or, for functions, older). `ADD COLUMN` was already guarded, triggers are created under `IF NOT EXISTS (SELECT .. FROM pg_trigger)`. What remains by design: `SET LOCAL statement_timeout = 0` and no `lock_timeout` (`pg_schema/mod.rs:51-58`) mean a real, first-time index build still waits; and the advisory-lock wait itself is unbounded. Not run: the PG test.

### E-F12, E-F13
See table and Decisions. For F13 the sub-claims are: (a) halt, (b) lease, (c) push-config, (d) rate-limit counter and audit store. (c) is covered by the E-F4 check in `build()` when the push store is unset; an explicitly chosen in-memory push store is accepted on purpose (the error message offers it). (d) is not covered: `RateLimitInterceptor` is not required by any profile, and `Auditable` accepts `InMemoryAuditStore` (`profile.rs` tests build with it).

### E-F18 (c)
`time_ms` uses the sealing replica's clock (`log.rs:192`), but the claim that purge deletes records younger than the floor is not right: `PostgresAuditStore::last_before` (`audit/postgres.rs:215-223`) takes the run of records older than the cutoff from the start of the chain, with a comment about exactly this case. What is left is an error bounded by the skew itself.

### E-F19
(a) the registry is per process (confirmed, harmless). (b) a stale entry is overwritten by the next `begin_run` on that replica and is read only for events that replica appends; the one gap is a failed `record_run_started` append (`audit/mod.rs:111`), which also exists on one replica. (c) `CancelTask` records no `runSeq` anywhere; the audit book (`audit.md:25`) lists "task, the caller, the trace" for it.

### E-F20
Race confirmed (the saved terminal precedes the log append by one round trip, and `finished()` synthesizes when the log has no terminal). The report also lists "the failure class" as lost; that is wrong: `failure_status` puts it on the status message (`execute.rs:427-437`), which `finished()` copies. Lost fields: `metadata.error` and budget fields on the event.

### E-F21
`DELETE .. WHERE ctid IN (SELECT ctid .. LIMIT n)` with two sessions: both subselects read the same rows (no `ORDER BY`), the second finds them deleted after the first commits, deletes 0, and `deleted == 0` ends it as `complete`. Rows beyond the first batch remain. Harmless to data; the docs' "disjoint" is wrong. With `SKIP LOCKED` the second takes the next rows.

### E-F22
(c) hot reload at different times per pod is inherent and bounded by `Cache-Control`; the ETag converges once all pods have the same card. (b) depends on user code signing at each boot; I found no doc that warns.

### E-F24 (conjecture in the README)
Reading settles the order of operations: `claim_send_key` (insert committed) -> `claimed_view` -> `try_claim_turn` (one SQL call) -> on `Busy` `release_send_key` -> wait. Between the first and the release a duplicate with the same key and message id on another replica takes the `Replay` branch. Not shown by reading: that anyone sends a duplicate that fast, and that B's wait then times out. Probe: in-process, a task store whose `turn_claims()` wraps the real one and sleeps 300 ms in `claim`; keyed send on B, same send on C at +100 ms, A holding the task past B's `executor_drain_timeout`; the bug is C answering with a task while B is refused.

### E-F25
Per idle stream, per pass of the hook loop (`subscribe.rs`, `sleep(interval)` at `:158`): `store.get` and, for a store with a log, `last_event_seq`, so 2 statements per 250 ms = 8 statements/s with a log and 4/s without. This matches the report's figure. The cost scales with idle streams and shares the pool with claim renewals; I did not measure where a 10-connection pool saturates.

### E-F26
`SqliteTurnClaims::renew` never checks expiry, so after a forward clock step the claim is live again at the owner's next tick (`renew_every`, 1 s). Only a claimer that arrives in that window can take it. A backward step delays takeover instead. The book says "one host" (`sqlite.md:6`); the explicit warning against network filesystems is only in the source comment (`claim/sqlite.rs:7-10`).
