# Triage of the S0 rows H2, H3 and H4

Done by the lead (the session that commissioned the other eight triage reports), on 2026-10-31, against `main` at `a0e667381e3a1be3b539aabbd45c046454d49b30` (the merge of pull request #184). Unlike the other reports, the checks below were **run** where this file says so; everything else is read. Environment: rustc 1.97.0, PostgreSQL 16.15, four vCPUs; tests built with `CARGO_INCREMENTAL=0 CARGO_PROFILE_DEV_DEBUG=0`.

## H2: the HTTP client cannot use a private CA or mTLS, and every `A2aClient` owns a separate pool

Split in two. Overall status: `fixed (part)`.

**(a) Private CA and mutual TLS: already fixed (audit row B-01).**

- Code: `ClientBuilder::with_tls_config` (`crates/a2a-protocol-client/src/builder/mod.rs:534`) stores `TlsConfig::Custom`; `http_client()` (`builder/transport_factory.rs:304-328`) builds the JSON-RPC and HTTP+JSON clients from it.
- Run: `cargo test -p a2a-protocol-client --test private_ca` → `4 passed; 0 failed`. The two tests that matter are `a_private_ca_is_refused_by_default_and_trusted_when_given` (both bindings; the refusal names `UnknownIssuer`) and `a_client_certificate_is_presented_when_given`.
- Mutation: in `http_client()`, `TlsConfig::Custom(tls) => (**tls).clone()` was replaced by `crate::tls::default_tls_config()`. The same command then reported `2 passed; 2 failed`, both failures being the two tests above. The file was restored and `git diff --stat` was empty.
- Not covered by this half: the card resolver, the client JWKS fetch and the token provider still have no code-level TLS option (audit row B-03); and the **server's** own outbound paths (push sender, JWKS and OIDC discovery, the OpenAI-compatible model client) ignore `SSL_CERT_FILE` and `HTTPS_PROXY` (finding N-B-1 in `B.md`, which reopens B-01 and B-02 as partial).

**(b) A shared pool, h2c and per-host limits: confirmed by reading.**

- `http_client()` calls `crate::tls::build_https_client_with_connect_timeout` once per `build()` and per binding (`transport_factory.rs:324`), which makes a new `hyper_util::client::legacy::Client` (`tls.rs:294-308`). Two `A2aClient`s to one host therefore hold two pools and two TLS session caches.
- A grep of `crates/a2a-protocol-client/src` for `HttpPool|with_http_pool|shared_pool|http2_only|h2c|pool_max_idle_per_host|max_conns` found nothing. `pool_idle_timeout` appears twice: `transport/mod.rs:60` (non-TLS build) and `tls.rs:305` (50 s). The only HTTP/2 enablement is ALPN over TLS (`proxy.rs:256,276`, `enable_http2`); plaintext HTTP is HTTP/1.1, so each open SSE stream holds a TCP connection.
- Decision for the maintainer (design): the report proposes an `HttpPool` handed to `ClientBuilder::with_http_pool`. Options: (1) that, as one `Arc` over the hyper client, default unchanged (one pool per client), documented as "one pool per process" for orchestrators; (2) make the pool process-global by default (fewer sockets, but cross-client interference and surprising lifetime); (3) only document a custom `Transport`. Recommendation: (1); it unblocks H6 (breaker state), H8 (card fetch cost) and H12. Size M; additive, so not breaking.

## H3: tasks orphaned by a crashed replica stay `working` forever, and their leases keep being renewed

Split in two. Overall status: `fixed (part)`.

**(a) Orphaned tasks: already fixed (audit row E-F1).**

- Code: `Reaper` (`crates/a2a-protocol-server/src/handler/claims/reaper/mod.rs`) looks every claim time-to-live for tasks that are `submitted` or `working`, hold no live claim and have not been written for that long (`TurnClaimStore::abandoned`; the SQL is `ABANDONED_PLAIN_SQL` and `ABANDONED_TENANT_SQL` in `store/claim/postgres.rs:52-64`, with the SQLite counterpart). It takes the claim, re-reads the task under it, ends it `failed` with failure class `transient`, and sends the webhooks.
- Run, SQLite: `cargo test -p a2a-protocol-server --features sqlite --lib -- reaper claims::reaper` → 3 passed (`sqlite_the_reaper_ends_only_what_nobody_runs`, `tenant_aware_sqlite_…`, `a_request_starts_the_handlers_reaper`).
- Run, PostgreSQL 16.15 (`A2A_TEST_POSTGRES_URL` set): `cargo test -p a2a-protocol-server --features sqlite,postgres --lib -- --ignored claims::reaper` → 2 passed (`postgres_…`, `tenant_aware_postgres_…`).
- Mutation: `if true { return Some(0); }` inserted at the top of `Reaper::look`; `--include-ignored claims::reaper` then reported `0 passed; 5 failed` (all five). Restored; `git diff --stat` empty.
- Not run here: a real replica killed with `SIGKILL` (the audit's live run of 2026-10-29 did that: the task was still `working` 70 s later before the reaper existed).

**(b) The lease of an orphan keeps being renewed: confirmed by reading (low).**

- The only caller of `LeaseStore::release` outside tests is the watcher task in the process that ran the turn (`handler/lease.rs:181`). When that process dies the lease row is never deleted. `Reaper` holds no lease store (its fields are `claims`, `task_store`, `push_config_store`, `push_sender`, `limits`, `metrics`), and nothing in `Reaper::fail` touches leases.
- `RequestHandler::renew_lease_if_asked` (`handler/lease.rs:119`) ignores both the boolean `LeaseStore::renew` returns and the task's state, so a `GetTask` that carries the lease extension renews the lease row of a task the reaper has already ended.
- Effect: a leaked row per orphaned leased task, and a renewal that "succeeds" for a finished task. The parent is not misled, because the `GetTask` it renews through returns the task as `failed`. Not reproduced by a test; the fix should add one that fails first (reaper ends a leased task → lease row gone).
- Window before the reaper acts: one claim time to live (15 s by default) plus up to one reaper interval.

## H4: delegation cancels its child on any stream blip, and has no durable journal or reattach

Overall status: `needs decision`. The defect is **confirmed by reading**; nothing was run.

- `Delegation::wait` (`crates/a2a-protocol-client/src/delegation/mod.rs:328`) matches `Some(Err(e)) => return self.lost(Some(e)).await` and `None => return self.lost(None).await` (lines 337-338). `Delegation::lost` (line 383) sends `cancel_task_in` to the child (line 387) and finishes with `Outcome::Lost`.
- Nothing resubscribes first. `EventStream::last_event_id` (`streaming/event_stream.rs:447`) and `A2aClient::subscribe_to_task_from` (`methods/tasks.rs:222`) exist, and the server replays from a `Last-Event-ID`; a grep of `src/delegation` for `reattach|resubscribe|DelegationJournal|with_resume|ResumePolicy` finds only a doc comment (`mod.rs:375`) that tells a caller to do it themselves.
- Tests that pin the current behaviour: `tests/delegation_tests.rs:176` `a_task_stream_that_ends_unsettled_is_lost_and_its_child_cancelled` and `:351` `a_lost_stream_cancels_the_child`.
- `docs/swarm-orchestration.md` lists G2 (durable child record plus reattach) as not done.
- Consequence at scale: an L4 reset, a proxy deploy, or the 5-minute `stream_idle_timeout` kills a healthy child, and the cancel cascades down the tree.

Options:

1. **Resume, then cancel; plus `Delegation::reattach`.** `lost()` first resubscribes from `last_event_id` under a bounded `ResumePolicy` (attempts, backoff, an overall deadline), and only then cancels. Add `Delegation::reattach(client, task_id, last_event_id)` so a supervisor that recorded the id (via `detach()`) can pick the child up after a restart. Client-only; additive. Size S to M. Default-on changes `Outcome::Lost` semantics, which is cheap now because 0.16.0 is unreleased.
2. **Option 1 plus a `DelegationJournal` trait** (record before the stream is opened, settle, list open records) with SQLite and PostgreSQL implementations, as the report proposes. This is G2 proper. Size L; needs an ADR.
3. **Document only**: tell supervisors to journal and reattach themselves. No code; leaves the S0 behaviour.

Recommendation: option 1 now, as its own pull request with a swarm-style test that cuts the stream mid-child and asserts the child completes; write the ADR for option 2 afterwards. Option 1 is also what H18 (ergonomics of wiring a child into its parent) should build on.
