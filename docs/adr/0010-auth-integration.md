# ADR 0010: First-party authentication helpers

**Status:** Accepted

**Date:** 2026-07

## Context

Through 0.6 the SDK modeled A2A security *schemes* (the agent card advertises
API-key/HTTP/OAuth2/OpenID Connect/mTLS schemes, and the type layer round-trips
them faithfully) and provided the *plumbing* to attach credentials — a client
`AuthInterceptor` that injects a stored header, and a server `ServerInterceptor`
trait that sees request headers and can reject a call. What it did **not**
provide was the *acquisition* and *verification* of tokens: a client had to run
its own OAuth2 flow to obtain a bearer token, and a server had to hand-roll JWT
signature verification to trust one. The official Python SDK ships both
(client-side `oauth2`/`openidconnect` acquisition, server-side `jsonwebtoken`
validation), so this was a real ergonomics and parity gap for anyone building a
production agent — and a security footgun, because "verify a JWT" is exactly
the kind of code that is easy to get subtly wrong.

## Decision

Add first-party auth helpers on both sides, built on the crypto and HTTP
stacks the SDK already depends on rather than pulling in the wider OAuth
ecosystem crates:

**Client (`a2a-protocol-client::token_provider`, no new feature):**

- A `TokenProvider` trait (`access_token()` per request) with a
  `StaticTokenProvider` and a `BearerAuthInterceptor` that injects a fresh
  token before every request — so a rotating/refreshing token stays current,
  including on retries.
- `OAuth2ClientCredentials`: the RFC 6749 §4.4 client-credentials grant against
  a token endpoint, with token caching, proactive refresh, single-flight
  concurrent refresh, and `Basic`/`Post` client-auth styles. Constructors read
  the token endpoint from an agent card's OAuth2 client-credentials flow, or
  discover it from an OIDC issuer.

**Server (`a2a-protocol-server::auth`):**

- `ApiKeyAuthInterceptor` and `BearerTokenAuthInterceptor` (no feature):
  constant-time comparison against an allowed set.
- `JwtAuthInterceptor` (feature `auth-jwt`): verifies HS256/RS256/ES256, checks
  `exp`/`nbf`/`iss`/`aud`, and resolves keys from a static `Jwks`, a shared
  HS256 secret, or a remote JWKS endpoint (cached with a TTL and refetched once
  on a key-id miss to follow rotation). OIDC discovery resolves the issuer's
  `jwks_uri`.

**Build on `ring` + `hyper`, not `oauth2`/`jsonwebtoken`/`openidconnect`.**
`ring` is already the crate's crypto backend (the `signing` feature uses it),
and `hyper` is already the HTTP core. The OAuth2 client-credentials grant is a
single form POST; JWT verification is base64url + a `ring` signature check plus
claim comparisons. Reimplementing exactly the slice we need — rather than
adopting three transitive-dependency-heavy crates and their differing rustls
versions — keeps ADR 0002's "minimal mandatory dependencies" intact and keeps
the whole auth surface auditable in a few hundred lines. The one dependency
added, behind `auth-jwt` only, is `base64` (tiny, already in-tree via
`signing`).

## Consequences

- **Only the client-credentials OAuth2 grant is built in.** Authorization-code
  (browser redirect) and device-code flows are interactive and out of scope
  for agent-to-agent auth; users needing them implement the `TokenProvider`
  trait. This is a deliberate scope line, documented at the call site.
- **JWT accepts exactly three algorithms** (HS256/RS256/ES256). `alg: none`
  and anything unlisted are rejected, and HS256 is only ever verified against a
  configured secret — never a JWKS public key — so the RS256→HS256 confusion
  downgrade is structurally impossible.
- **Rejections map to `InvalidRequest` (HTTP 400 / gRPC `INVALID_ARGUMENT`),
  not 401.** The A2A error set has no unauthenticated code (the spec models
  auth at the transport/security-scheme layer), and the interceptor abstraction
  produces an `A2aError` with a fixed status. Deployments needing true `401`
  with `WWW-Authenticate` terminate auth at a gateway; these helpers are the
  self-contained, defense-in-depth option. The rejection message is generic so
  it cannot be used as an oracle.
- **Verification is cross-checked against an independent implementation.** The
  JWT test vectors are generated by Python's `cryptography`/`hmac` and verified
  here through `ring`, so a bug in either implementation surfaces as a test
  failure rather than silent acceptance. A live end-to-end test drives the full
  interceptor → dispatcher path over real HTTP, including JWKS fetch, cache, and
  rotation refetch.

## Alternatives considered

- **Depend on `oauth2` + `jsonwebtoken` + `openidconnect`** (the Python SDK's
  shape). Rejected: three heavy dependency trees, their own (often lagging)
  rustls/ring versions to reconcile against ours, and far more surface than the
  A2A auth story needs. The confusion-attack and `alg:none` defenses would then
  live in someone else's code we'd still have to audit.
- **Leave acquisition/verification to the user** (the 0.6 status quo). Rejected:
  it is the gap this ADR exists to close, and "verify a JWT yourself" is a
  well-known source of security bugs.
